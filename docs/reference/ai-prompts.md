# 运维 AI Prompt 与 Agent 指令模板速查

> 把日常运维任务（解释命令、写脚本、诊断日志、审配置）打包成可直接复制的 Prompt 模板。
> 用法：复制下方代码块 → 替换占位符（`<...>`）→ 粘贴给任意 LLM。右侧「本页目录」可跳转。
> 原理与进阶见 [AI Agent 基础](/guide/aiops-agent-basics)、[Agent 运维实战](/guide/aiops-agent-practice)、[MCP 协议](/guide/aiops-mcp)。

::: warning 使用前提
- **先脱敏**：把真实 IP、域名、密钥、密码、用户名、内部主机名替换成 `<IP>`、`<域名>`、`<token>` 再粘贴。
- **结果需人工核对**：AI 会一本正经地编造命令/版本，涉及生产的操作必须先在测试环境验证。
- **高危操作不得直接执行**：`rm -rf`、`DROP`、`reset --hard`、`drop` 库等，让 AI 先给方案与回滚步骤，人来拍板。
:::

## 通用指令框架

任何 Prompt 都按这五块组织，效果远好于"帮我看看这个报错"：

```text
【角色设定】你是一名有 10 年经验的 Linux SRE / 运维专家，熟悉 <发行版/技术栈>。
【任务目标】我希望你 <具体要做的事，例如：帮我解释这条命令的每一个参数 / 诊断下面这段报错>。
【背景上下文】系统是 <Rocky 9 / K8s 1.35 / MySQL 8.0>，我已经做了 <尝试过的操作>，现象是 <现象>。
【约束条件】不要使用晦涩术语，面向初级运维讲解；给出可直接复制的命令；如涉及生产高危操作要先提示风险并给出回滚方案。
【期望输出格式】用 <表格 / 分步骤编号 / 代码块> 输出，最后用 3 条要点总结。
```

## 1. 解释一条命令 / 一段配置

```text
【角色】你是资深 Linux 运维，擅长把命令讲给新手听。
【任务】请逐条解释下面这条命令每个部分的含义，并说明它在什么场景下用、有什么风险：

<在这里贴命令，例如：find /var/log -name "*.log" -mtime +7 -delete>

【输出】先给一句大白话总结，再用表格拆分每段，最后列 2 个使用注意事项。
```

适用：拿到一条看不懂的一行流命令，搞清楚它到底干了什么再执行。

## 2. 解释一段配置（Nginx / BIND / MySQL）

```text
【角色】你是 Web/数据库运维专家。
【任务】下面是我的 <Nginx/MySQL/BIND> 配置，请逐段解释作用，并指出可能存在的安全或性能问题：

<粘贴配置>

【约束】用小白能懂的类比解释关键配置；发现问题按"严重/一般/建议"分级；不要改动我的配置逻辑，只给诊断和可选优化建议。
```

## 3. 生成 Shell / Python 脚本

```text
【角色】你是 Python/Shell 自动化工程师，写过大量生产运维脚本。
【任务】帮我写一个 <功能，例如：监控磁盘使用率超过 80% 就发企业微信告警的脚本>。
【背景】系统 <Rocky 9>，已有 <curl 告警接口>，要检查的挂载点 <data>。
【要求】
1. 用 bash 或 Python3，给出完整可运行代码块；
2. 加详细中文注释；
3. 包含错误处理、日志、退出码；
4. 说明如何加入 crontab；
5. 先给我测试环境验证方法，再给上线注意事项。
```

适用：重复劳动脚本化。注意让 AI 给出验证方法，不要直接上线。

## 4. 报错日志诊断（贴日志）

```text
【角色】你是排查过千万级日志的 SRE 专家。
【任务】下面是我的 <服务名> 报错日志，请帮我定位根本原因，并给出排查步骤和修复命令。

==== 日志开始 ====
<在这里粘贴完整报错堆栈 / 日志，已脱敏>
==== 日志结束 ====

【背景】我已经确认 <已排除的可能，例如：磁盘没满、网络通>；最近变更 <变更内容或"无变更">。
【输出】
1. 用一句话说最可能的根因；
2. 按可能性从高到低列出 3 个候选原因，每个配一条验证命令；
3. 给出修复命令（标注哪些是只读排查、哪些是变更操作）；
4. 给回滚方案。
```

适用：贴 Java Stack Trace、MySQL 报错、Nginx 502、BIND 启动失败。注意日志长时一次贴全，别只贴最后两行。

## 5. 告警分析

```text
【角色】你是值班 SRE。
【任务】这是一条告警：<告警名称、触发时间、当前值、阈值>。
【背景】相关服务 <服务名>，依赖 <数据库/下游服务>。
【要求】
1. 判断这是不是真故障，先给"最可能的 3 个原因"；
2. 列出按顺序的排查命令（从最容易验证的开始）；
3. 给出临时缓解措施和根治方向；
4. 如果是误报，给出怎么调告警阈值。
```

适用：凌晨告警起来懒得想，先让 AI 给排查路径兜底。

## 6. 系统性能分析（贴 top / iostat 输出）

```text
【角色】你是性能优化专家，熟悉 Linux 性能三角（CPU/内存/磁盘IO/网络）。
【任务】下面是我在一台变慢的机器上采集的 <top / iostat -x / vmstat / ss -s> 输出，请分析瓶颈在哪：

<粘贴 top 或 iostat 输出>

【要求】
1. 指出最可疑的瓶颈（CPU 高 / 内存耗尽 / IO 等待 / 网络）并给数据依据；
2. 给出下一步定位命令（如 pidstat、perf、dstat）；
3. 给临时处理建议和长期优化方向；
4. 不要臆测，说清楚哪个数字支持你的结论。
```

适用：机器突然变慢。多贴几组间隔采样的输出，结论更准。

## 7. 配置 / 代码安全审查

```text
【角色】你是安全运维 / DevSecOps 工程师。
【任务】请审查下面的 <Nginx 配置 / Shell 脚本 / K8s YAML>，找出安全与规范问题：

<粘贴内容>

【要求】按"高危/中危/低危"分级列出问题，每条说明风险、修复方法和可直接替换的代码；重点检查：权限过大、明文密钥、未校验输入、暴露管理端口、缺少超时/限流。
```

## 8. 生成 Runbook / 应急预案

```text
【角色】你是做过多次故障复盘的 SRE 负责人。
【任务】为 <服务名 / 故障场景，例如：MySQL 主库宕机> 写一份值班 Runbook。
【要求】包含：
1. 故障确认与分级；
2. 按时间线的处置步骤（每步给命令和预期结果）；
3. 升级路径与通知对象（写成占位符）；
4. 回退方案；
5. 复盘要收集的数据清单。
用编号步骤输出，命令用代码块。
```

适用：把口头经验沉淀成团队可执行的应急预案。

## 9. SQL 与正则

```text
【任务】
1. 写一条 <MySQL> 查询：<需求，例如：统计最近 7 天每天的订单量并按数量倒序>，表结构为 <粘贴建表语句>。
2. 帮我写一个正则：<需求，例如：从 Nginx 日志里提取状态码和响应时间>，日志样例：<贴一行真实日志>。
【要求】先解释思路，再给可直接运行的 SQL / 正则，并给一个验证用的小例子。
```

## 10. 把概念讲给小白听

```text
【角色】你是擅长类比的运维讲师。
【任务】请给一个刚入行、只会装系统的新手，讲清楚 <概念，例如：什么是 Linux 的 inode / 什么是 K8s 的 Service / 什么是 eBPF>。
【要求】
1. 先给一个生活化的类比（不要用技术名词解释技术名词）；
2. 再讲它解决了什么问题；
3. 给一个最小可操作的例子命令；
4. 控制在 300 字以内，避免堆砌术语。
```

适用：自己学新概念时让 AI 降维解释，建立直觉后再看官方文档。

## 11. 变更方案评审

```text
【角色】你是变更评审委员会的资深 SRE，习惯挑毛病。
【任务】我计划在生产执行以下变更：<描述变更，例如：把 Nginx worker_connections 从 1024 调到 65535 / 给 MySQL 加从库>。
【背景】当前配置 <现状>，业务高峰 <时间>。
【要求】
1. 找出这个方案可能忽略的风险点（至少 5 个）；
2. 指出可能的副作用和回滚方式；
3. 建议分批/灰度发布步骤；
4. 列出变更前后要观察的指标。
```

适用：动手前让 AI 当"挑刺的同事"，补齐盲区。

## 12. 多 Agent 角色分工指令（诊断 / 执行 / 复核）

```text
请你同时扮演三个角色，按顺序协作处理下面这个运维故障，每个角色的输出用对应标题分隔：

【诊断官】只负责分析和给出方案，不执行。先根据下面的现象列出最可能的根因和验证命令。
【执行官】只在诊断官确认根因后，给出最小化的修复命令序列，每条命令标注风险等级。
【复核官】站在对立面审查执行官的命令：哪些可能误删数据、哪些没考虑回滚、哪些需要先备份；给出最终修正版。

故障现象：<粘贴现象与日志，已脱敏>
```

适用：复杂故障处理。关键是让"复核官"独立挑刺，避免 AI 一口气给出危险命令。
