# 网络基础

::: tip 本篇定位
建立系统的网络知识框架：网络分层模型（**OSI/TCP-IP**）、**IP 地址与子网划分**、**TCP/UDP**、以太网与 MAC、Linux 网卡配置（nmcli/netplan）和网卡高可用。网络排障命令（ping、tcpdump、nmap、nc、traceroute、dig 等）见 [网络命令速查](/reference/network-commands)。

## 一、网络基础概念

### 1.1 什么是计算机网络

把地理位置不同、具有独立功能的多台计算机及外部设备，通过通信线路和网络设备连接起来，在网络协议管理下实现**资源共享和信息传递**的系统。

### 1.2 网络范围分类

| 类型 | 全称 | 范围 |
|---|---|---|
| **LAN 局域网** | Local Area Network | 小范围（办公室、机房、园区），通常 10km 内，一个单位 |
| **MAN 城域网** | Metropolitan | 覆盖一个城市，连接多个局域网 |
| **WAN 广域网** | Wide Area Network | 跨城市/国家，覆盖全球（Internet 即最大的广域网） |

### 1.3 网络拓扑

拓扑指节点之间的连接方式：

| 拓扑 | 特点 |
|---|---|
| 总线型 | 所有节点共用一条线路，省成本、易布线，但单点故障影响大 |
| 星型 | 节点都连到中心设备（交换机），易管理扩展，中心是关键 |
| 环型 | 节点首尾成环，数据单向传输 |
| 网状型 | 节点间多条链路互联，可靠性高、冗余好（广域网/数据中心） |

现代局域网主流是**星型**（经交换机），核心/骨干追求网状冗余。

### 1.4 网络组成

- **终端/主机**：计算机、服务器、手机等；
- **网络设备**：网卡、集线器（Hub）、交换机（Switch）、路由器（Router）；
- **通信线路**：网线、光纤、无线；
- **协议与软件**：TCP/IP 等通信规则、操作系统、应用。

## 二、网络分层模型

### 2.1 为什么要分层

网络通信极其复杂，分层把整体功能拆成多个层次，每层只负责一类功能、通过标准接口与相邻层协作，实现**解耦、标准化、独立演进、便于排障**。

### 2.2 OSI 七层模型（理论标准）

从下到上：

| 层 | 名称 | 功能 | 数据单元 | 典型协议/设备 |
|---|---|---|---|---|
| 7 | 应用层 | 面向用户的网络服务 | 数据 Data | HTTP、DNS、DHCP、FTP、SMTP |
| 6 | 表示层 | 数据编码、加密、压缩 | — | SSL/TLS、JPEG |
| 5 | 会话层 | 建立/管理/断开会话 | — | — |
| 4 | 传输层 | 端到端传输、端口、可靠性 | 段 Segment | **TCP、UDP** |
| 3 | 网络层 | 寻址与路由选择 | 包 Packet | **IP、ICMP、ARP**、路由器 |
| 2 | 数据链路层 | 同一链路内帧传输、MAC | 帧 Frame | 以太网、**MAC**、交换机 |
| 1 | 物理层 | 比特流传输 | 比特 Bit | 网线、光纤、集线器 |

记忆口诀（从下到上）：**物、数、网、传、会、表、应**。

### 2.3 TCP/IP 模型（实际标准）

实际互联网使用 TCP/IP 模型，教学中常用"五层模型"对照：

| OSI 七层 | TCP/IP 四层 | 五层教学模型 |
|---|---|---|
| 应用/表示/会话 | **应用层** | 应用层 |
| 传输 | **传输层** | 传输层 |
| 网络 | **网际层（IP）** | 网络层 |
| 数据链路/物理 | **网络接口层** | 数据链路层 / 物理层 |

### 2.4 封装与解封装

发送数据时，数据从上到下**逐层加首部（封装）**：应用数据 → 加 TCP 头成"段" → 加 IP 头成"包" → 加帧头帧尾成"帧" → 转成比特发出。接收时从下到上**逐层去掉首部（解封装）**。

```
应用数据
[TCP头][数据]            ← 段 Segment
[IP头][TCP头][数据]       ← 包 Packet
[帧头][IP头][TCP头][数据][帧尾]  ← 帧 Frame
```

## 三、网络层：IP 协议

### 3.1 IPv4 地址

IPv4 是 32 位地址，用**点分十进制**表示为 4 段（每段 0-255），如 `192.168.1.10`。

### 3.2 地址分类（有类编址）

| 类 | 范围 | 默认掩码 | 用途 |
|---|---|---|---|
| A | 1.0.0.0 – 126.x | /8 | 大型网络 |
| B | 128.0 – 191.255 | /16 | 中型网络 |
| C | 192.0 – 223.255 | /24 | 小型网络 |
| D | 224.0 – 239.255 | — | 组播 |
| E | 240.0 – 255.255 | — | 保留实验 |

**私有地址（内网使用，不能在公网路由）：**

| 类 | 私有网段 | 范围 |
|---|---|---|
| A | `10.0.0.0/8` | 10.0.0.0 – 10.255.255.255 |
| B | `172.16.0.0/12` | 172.16.0.0 – 172.31.255.255 |
| C | `192.168.0.0/16` | 192.168.0.0 – 192.168.255.255 |

**特殊地址：**

| 地址 | 含义 |
|---|---|
| 127.0.0.0/8 | 回环地址（本机测试） |
| 0.0.0.0 | 本机所有地址 / 默认路由 |
| 255.255.255.255 | 受限广播 |
| 169.254.0.0/16 | link-local（DHCP 失败时自动配置） |

### 3.3 子网掩码与 CIDR

IP 地址 = **网络号 + 主机号**，子网掩码用来区分二者。

- 掩码连续的 1 对应网络位，0 对应主机位；
- **CIDR** 用 `/位数` 表示网络位，如 `192.168.1.10/24`（前 24 位是网络号）；
- `/24` 掩码 `255.255.255.0`，网络号 `192.168.1.0`。

### 3.4 子网划分

通过**借主机位**把一个大网络切成多个小子网：

- 借 `n` 位 → 分出 `2^n` 个子网；
- 主机位剩 `h` 位 → 每个子网 `2^h` 个地址，**可用主机 `2^h - 2`**（减去网络地址和广播地址）。

**示例：把 192.168.1.0/24 切成 /26（借 2 位）：**

| 子网 | 网络地址 | 可用主机范围 | 广播地址 |
|---|---|---|---|
| 1 | 192.168.1.0/26 | .1 – .62 | .63 |
| 2 | 192.168.1.64/26 | .65 – .126 | .127 |
| 3 | 192.168.1.128/26 | .129 – .190 | .191 |
| 4 | 192.168.1.192/26 | .193 – .254 | .255 |

每个 /26 有 64 个地址、62 个可用主机。

### 3.5 IPv6 简介

IPv4 地址已枯竭，**IPv6** 用 128 位，写成 8 组十六进制（冒号分隔），如 `2001:0db8::1`，地址空间极大、内置安全和自动配置，正在逐步普及。

### 3.6 ICMP 与 ARP

- **ICMP（网际控制报文协议）**：用于网络诊断和差错报告，`ping`（探测主机可达）和 `traceroute`（追踪路径）基于 ICMP；
- **ARP（地址解析协议）**：在局域网内根据 IP 地址解析出对应的 **MAC 地址**（`arp -n`、`ip neigh`）。

## 四、传输层：TCP 与 UDP

### 4.1 端口

传输层用**端口号**区分同一主机上的不同应用（0-65535），IP 定位主机、端口定位进程。

| 端口 | 服务 |
|---|---|
| 22 | SSH |
| 80 / 443 | HTTP / HTTPS |
| 53 | DNS |
| 21 / 20 | FTP |
| 25 / 110 / 143 | SMTP / POP3 / IMAP |
| 123 | NTP |
| 3306 / 6379 | MySQL / Redis |
| 67、68 | DHCP |

- 0-1023 为知名端口（需特权）；1024-49151 注册端口；以上为动态端口。

### 4.2 TCP：面向连接、可靠

**TCP 特点：** 面向连接、可靠传输（确认重传）、有序、流量控制和拥塞控制，开销较大。

**三次握手（建立连接）：**

```
客户端                          服务端
  │ ── SYN (seq=x) ───────────→ │      客户端 SYN_SENT
  │ ←── SYN+ACK (ack=x+1) ───── │      服务端 SYN_RCVD
  │ ── ACK (ack=y+1) ─────────→ │      双方 ESTABLISHED
```

**四次挥手（断开连接）：**

```
主动方                          被动方
  │ ── FIN ───────────────────→ │
  │ ←── ACK ─────────────────── │      被动方 CLOSE_WAIT
  │ ←── FIN ─────────────────── │
  │ ── ACK ───────────────────→ │      主动方 TIME_WAIT → CLOSED
```

::: details 为什么握手 3 次、挥手 4 次
- 握手时服务端的 SYN 和 ACK 可以合并成一条，故 3 次；
- 挥手时被动方收到 FIN 后先回 ACK，但可能还有数据要发，等数据发完再发 FIN，ACK 和 FIN 分开发，故 4 次；
- `TIME_WAIT` 等待约 2MSL，确保最后的 ACK 到达、旧连接报文消散。
:::

### 4.3 UDP：无连接、快

**UDP 特点：** 无连接、不保证可靠和顺序、无拥塞控制，首部小、延迟低、开销小，适合实时场景（DNS 查询、视频/语音、游戏）。

### 4.4 TCP vs UDP

| 对比 | TCP | UDP |
|---|---|---|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠（确认重传排序） | 不保证 |
| 传输方式 | 字节流 | 数据报 |
| 开销/速度 | 较大、较慢 | 小、快 |
| 头部 | 20 字节起 | 8 字节 |
| 场景 | 网页、文件、邮件、数据库 | DNS、直播、语音、游戏 |

## 五、数据链路层与以太网

### 5.1 MAC 地址

- **MAC 地址**是网卡的物理地址，48 位、十六进制，如 `00:0c:29:8a:3b:1f`，全球唯一，烧录在网卡上；
- 局域网内数据帧靠 MAC 地址投递，ARP 负责 IP→MAC 解析。

### 5.2 以太网

以太网是主流的局域网技术（IEEE 802.3），通过交换机按 MAC 转发帧，采用 CSMA/CD 机制（早期共享介质）。

### 5.3 VLAN

**VLAN（虚拟局域网，IEEE 802.1Q）** 在交换机上把一个物理网络逻辑上划分为多个广播域，隔离不同部门/业务的二层流量，提升安全和管理灵活性，通过在帧中打 VLAN 标签实现。

### 5.4 通信方式

- **单播（Unicast）**：一对一；
- **广播（Broadcast）**：一对所有（目标 MAC 全 F）；
- **组播（Multicast）**：一对一组（D 类 IP）。

## 六、网卡与网络配置

### 6.1 网卡命名

- 旧规则：`eth0`、`eth1`；
- systemd **可预测命名**：`eno1`（板载 onboard）、`ens33`（插槽 slot）、`enp0s3`（PCI 位置）；`wl` 开头为无线网卡。
  - `en` = 以太网，`o` = 板载，`s` = 热插拔槽，`p` = PCI 总线位置。

### 6.2 查看网络信息

```bash
ip addr            # 或 ip a：查看网卡和 IP（替代 ifconfig）
ip route           # 查看路由表/默认网关（替代 route -n）
ss -tunlp          # 查看监听端口（替代 netstat）
ip neigh           # ARP 表
```

### 6.3 RHEL/Rocky：nmcli 配置

RHEL 系用 **NetworkManager** 管理网络，命令行工具 `nmcli`、文本界面 `nmtui`。

```bash
nmcli connection show                  # 查看连接（con）
nmcli device status                    # 查看设备（d）

# 修改连接（静态 IP）
nmcli con mod ens33 \
  ipv4.method manual \
  ipv4.addresses 10.0.0.13/24 \
  ipv4.gateway 10.0.0.2 \
  ipv4.dns "223.5.5.5,114.114.114.114"
nmcli con up ens33                     # 激活生效

# 自动获取（DHCP）
nmcli con mod ens33 ipv4.method auto && nmcli con up ens33
```

- 新系统连接配置文件在 `/etc/NetworkManager/system-connections/`（keyfile 格式）；
- 旧版在 `/etc/sysconfig/network-scripts/ifcfg-ens33`。

### 6.4 Ubuntu：netplan 配置

Ubuntu 18.04+ 用 **netplan** 管理，配置文件在 `/etc/netplan/*.yaml`（**YAML 严格缩进**）：

```yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    eth0:
      addresses:
        - 10.0.0.13/24
      routes:
        - to: default
          via: 10.0.0.2
      nameservers:
        addresses: [223.5.5.5, 114.114.114.114]
```

```bash
sudo netplan generate
sudo netplan apply          # 应用生效
# 桌面版用 NetworkManager 时 renderer: NetworkManager
```

DHCP 写法：`eth0: {dhcp4: true}`。

### 6.5 主机名

```bash
hostname                              # 查看
sudo hostnamectl set-hostname blog-host # 永久修改（写入 /etc/hostname）
```

### 6.6 路由配置

```bash
ip route                              # 查看默认路由
sudo ip route add default via 10.0.0.2            # 添加默认网关
sudo ip route add 192.168.2.0/24 via 10.0.0.254   # 添加静态路由
sudo ip route del 192.168.2.0/24                  # 删除
```

### 6.7 连通性诊断思路

排障遵循**由近及远、分层排查**：

1. 看网卡/IP：`ip a`；
2. ping 本机、ping 网关（二层/本地）；
3. ping 外网 IP（如 `ping 223.5.5.5`，测路由）；
4. ping 域名（不通则 DNS 问题）；
5. 看端口/服务：`ss -tunlp`、`curl`；
6. 抓包：`tcpdump`。

> 完整命令参数见 [网络命令速查](/reference/network-commands)。

## 七、网卡高可用（了解）

### 7.1 网卡绑定 Bond

把多块物理网卡绑定成一个逻辑接口，实现**冗余（高可用）和/或带宽叠加**。

| mode | 名称 | 说明 |
|---|---|---|
| 0 | balance-rr | 轮询，负载均衡+容错（需交换机配合） |
| 1 | active-backup | **主备**，只有一块工作，故障切换（最常用、无需特殊交换机） |
| 2 | balance-xor | 基于 MAC 哈希 |
| 3 | broadcast | 广播，所有网卡发相同数据 |
| 4 | 802.3ad | LACP 动态链路聚合（需交换机支持） |
| 5 | balance-tlb | 发送负载均衡 |
| 6 | balance-alb | 收发负载均衡 |

### 7.2 team vs bond

- **bond**：传统内核绑定，成熟稳定；
- **team**：新一代链路聚合，用户态守护进程、模块化设计、支持更多负载策略和更好的性能监控；
- 新项目可评估 team，但 bond 资料更全、兼容性好，生产仍常用。

### 7.3 bridge 桥接

**Linux 网桥（bridge）** 工作在二层，像虚拟交换机把多个接口（含虚拟机/容器网卡）桥接在一起，虚拟化/容器场景常用（`brctl`、`bridge link`）。

### 一、部署前：协议基础

<details>
<summary>Q1：TCP 为什么三次握手、四次挥手？</summary>

**答：**

结论先说：三次握手是为了**双方都确认彼此的收发能力正常**，并同步初始序列号；四次挥手是因为 TCP 全双工，两个方向要各自关闭。

第一次，客户端发 `SYN`，带初始序号 `seq=x`，表示"我想连你，我的起始序号是 x"。第二次，服务端回 `SYN+ACK`，`ack=x+1`、`seq=y`，表示"我收到了，也同意连你，我的起始序号是 y"。第三次，客户端再发 `ACK`，`ack=y+1`，表示"我也收到你的序号了"。三次之后双方都知道对方能收能发。为什么不是两次？因为如果只有两次，历史重复的 SYN 会让服务端白等资源——第三次握手就是让服务端确认客户端此刻真的在线。

挥手要四次是因为全双工：主动方发 `FIN` 表示"我不发了"，被动方先回 `ACK`，但此时被动方可能还有数据要发，等它发完再发自己的 `FIN`，主动方再回 `ACK`。所以 FIN 和 ACK 不能合并，要分四次。

最后一个关键点：主动关闭方发完最后一个 ACK 后要进 `TIME_WAIT`，等 `2MSL`（最大报文生存时间的两倍）。原因是要保证最后一个 ACK 能到达对方（丢了对方会重发 FIN），同时让本次连接的所有旧报文在网络中消亡，避免影响下一条同四元组的连接。线上如果 `TIME_WAIT` 过多，可以开 `tcp_tw_reuse`，但不要轻易开 `tw_recycle`（NAT 场景会出问题）。

</details>

<details>
<summary>Q2：TCP 和 UDP 区别及场景？</summary>

**答：**

结论：TCP 是面向连接、可靠、字节流的协议；UDP 是无连接、尽力而为、数据报的协议。

第一，TCP 面向连接，要先三次握手，断开要四次挥手；UDP 发数据前不需要握手，直接往 socket 里写就行，所以延迟低、开销小。

第二，TCP 保证可靠：有序列号、确认应答、超时重传、滑动窗口、拥塞控制（慢启动、拥塞避免、快重传、快恢复），数据按序到达、不丢不重。UDP 不保证，丢了就丢了、后发的可能先到，可靠性由应用层自己做。

第三，TCP 是字节流，没有报文边界，会粘包；UDP 是一条一条的数据报，有边界，发多大收多大。

第四，开销上 TCP 头部至少 20 字节，还要维护连接状态、拥塞窗口；UDP 头部只有 8 字节。

场景上：要求可靠传输的用 TCP，比如 HTTP/HTTPS、SSH、MySQL、Redis、文件下载、邮件；要求低延迟、能容忍少量丢包的用 UDP，比如 DNS 查询（53 端口）、视频会议、直播、游戏实时位置、QUIC/HTTP3、NTP。现在很多新场景（WebRTC、游戏）干脆在 UDP 上自己做一层可靠传输，就是为了既快又可控。

</details>

<details>
<summary>Q3：HTTPS 加密过程？</summary>

**答：**

结论：HTTPS = HTTP + TLS，核心思想是**用非对称加密协商出一个对称密钥，之后全程对称加密**，再用证书证明服务器身份。

简化流程（TLS 1.2 为例）：第一，客户端 `Client Hello`，带上支持的 TLS 版本、加密套件列表、一个随机数 `client random`。第二，服务端 `Server Hello`，选定加密套件，给另一个随机数 `server random`，然后把自己的证书（含公钥、域名、有效期、CA 签名）一起发回来。第三，客户端验证证书：先看证书链能不能追溯到本机信任的根 CA，再看域名是否匹配、是否过期、有没有被吊销（CRL/OCSP）。验证通过后，客户端生成一个 `pre-master secret`，用服务器公钥加密发过去。第四，双方用 `client random + server random + pre-master secret` 各自算出会话密钥 `session key`。第五，之后所有业务数据都用这个对称密钥（AES-GCM 之类）加密传输。

TLS 1.3 把这个过程压缩到 1-RTT，甚至 0-RTT，握手更快，并且废弃了 RSA 密钥交换、固定用 ECDHE 前向 secrecy——意思是即使服务器私钥以后泄露，历史抓包也解不开，这就是前向安全。

为什么不全用非对称？因为非对称太慢，不适合传大量数据；为什么不全用对称？因为对称密钥怎么安全地交给对方是个死结。所以两者结合：非对称解决"密钥怎么安全传"，对称解决"数据怎么快加密"。

</details>

<details>
<summary>Q4：常见 HTTP 状态码？</summary>

**答：**

结论：状态码分 5 类，3 位数字，第一位是大类。我按类背。

2xx 成功：`200 OK` 正常返回；`201 Created` 新建成功（POST）；`204 No Content` 成功但没返回体，常用于 DELETE。

3xx 重定向：`301 Moved Permanently` 永久重定向，浏览器会缓存，换域名、HTTP 跳 HTTPS 用；`302 Found` 临时重定向，每次都重新请求；`304 Not Modified` 协商缓存命中，浏览器带 `If-None-Match`/`If-Modified-Since`，服务器资源没变就回 304，浏览器用本地缓存。注意 301/302 历史上 POST 会被改成 GET，303/307/308 专门规范了这一点，307/308 保持方法不变。

4xx 客户端错误：`400 Bad Request` 请求参数/格式错；`401 Unauthorized` 没登录或 token 失效，要认证；`403 Forbidden` 认证了但没权限；`404 Not Found` 路由/资源不存在；`405 Method Not Allowed` 方法不对；`429 Too Many Requests` 触发限流。

5xx 服务端错误：`500 Internal Server Error` 后端代码抛异常；`502 Bad Gateway` 反向代理（Nginx）拿不到后端响应，后端挂了或端口不通；`503 Service Unavailable` 服务暂时不可用，一般是过载或维护；`504 Gateway Timeout` 代理等后端超时了。

实际排障最容易混淆的是 502 和 504 的区别：502 是"连都没连上/后端直接拒了"，504 是"连上了但后端处理太慢超时"。排查思路我在 Nginx 那题展开。

</details>

### 二、部署与接入：DNS 与端口

<details>
<summary>Q5：DNS 解析过程？</summary>

**答：**

结论：浏览器输入域名后，DNS 查询走一个**多级缓存 + 递归迭代**的过程。

第一步，先查浏览器自身缓存（Chrome 有 1 分钟左右的 DNS 缓存），没命中再查操作系统缓存（`nscd`/`systemd-resolved`），再读 `/etc/hosts`。

第二步，还没命中就发请求给**本地递归 DNS**，也就是 `/etc/resolv.conf` 里配的那个（一般是运营商或 223.5.5.5、119.29.29.29）。这一步对客户端来说是**递归查询**——我要一个最终答案，你别让我再跑。

第三步，递归服务器自己开始**迭代查询**：先问根域名服务器（`.`，全球 13 组根），根说".com 的事你去找顶级域服务器"；再问 `.com` 顶级域，它说"`example.com` 去找它的权威 NS"；最后问权威服务器，拿到 A 记录 `1.2.3.4`。

第四步，递归服务器把结果缓存下来（按 TTL），返回给客户端，客户端也缓存一份。

常用记录类型：`A` 把域名转 IPv4；`AAAA` 转 IPv6；`CNAME` 别名，指向另一个域名；`MX` 邮件服务器；`NS` 指定该域的权威服务器；`TXT` 做 SPF/域名验证。

排查用 `dig example.com`，重点看 `ANSWER SECTION` 和 `Query time`；`dig +trace` 看完整迭代路径；`dig @8.8.8.8 example.com` 指定别的 DNS 服务器对比。线上域名突然解析错，第一件事就是 `dig` 对比本地和公共 DNS 的结果，再看是不是 TTL 没生效还是权威记录被改了。

</details>

<details>
<summary>Q6：端口不通怎么排查？</summary>

**答：**

结论：端口不通按"**服务有没有监听 → 防火墙放没放行 → 包有没有到达 → 客户端连没连上**"四段查。

第一段，服务端看监听。`ss -tlnp | grep 8080`（或 `netstat -tlnp`），看这个端口有没有进程在 LISTEN，绑的是 `0.0.0.0` 还是 `127.0.0.1`——如果只绑本地回环，外部根本连不进来，要改成 `0.0.0.0` 或具体网卡 IP。没监听就去查服务为什么没起来：`systemctl status xxx`、`journalctl -u xxx -f`、看应用日志。

第二段，看防火墙。`iptables -L -n -v` 看 INPUT 链；`firewall-cmd --list-all`（firewalld）；`ufw status`（Ubuntu）。云服务器还要去控制台看安全组，很多人服务器内部防火墙关了但安全组没放行 8080。

第三段，确认包到底有没有到服务器。在服务端抓包：`tcpdump -i any port 8080 -nn`，然后从客户端 `nc -vz server_ip 8080`。如果抓包完全没看到 SYN 进来，说明包被中间网络/安全组拦了；如果看到 SYN 进来但没回 SYN+ACK，那是本机防火墙 DROP 了；如果 SYN+ACK 都回了但客户端说连不上，那是回程路由或 conntrack 问题。

第四段，客户端这边再确认：`telnet server_ip 8080`、`nc -vz server_ip 8080`、`curl -v telnet://server_ip:8080`。也可以在服务端本机先 `curl 127.0.0.1:8080` 自检，本地通外部不通，问题一定在网络路径/防火墙层。

容器场景还要加一步：`docker ps` 看端口映射 `-p 8080:80` 有没有写对，`docker inspect <容器>` 看实际映射到哪个宿主端口。

</details>

### 三、运行与排障：从现象到证据

<details>
<summary>Q7：网站打不开如何系统排查？</summary>

**答：**

结论：从客户端到服务端**一层一层往下剥**，先定位是哪一层断了，再在那一层深挖，不要一上来就登服务器。

第一，先确认本机网络。`ping baidu.com` 看通不通；如果 ping 域名不通但 `ping 220.181.38.148` 通，那就是 DNS 问题，转第三层。如果连 IP 都不通，`ping 网关`、`ip route` 看默认路由，`ip addr` 看自己有没有拿到地址。

第二，测端口。`telnet example.com 443` 或 `nc -vz example.com 443`，TCP 三次握手能不能完成。不通就 `traceroute example.com` 或 `mtr --tcp --port 443 example.com` 看路径上哪一跳开始丢包。

第三，查 DNS。`dig example.com` 或 `nslookup example.com`，看返回的 A 记录对不对；`dig +trace example.com` 看递归到哪一步挂了。必要时换 `dig @223.5.5.5 example.com` 对比公共 DNS，判断是本地解析器问题还是权威记录问题。

第四，测应用层。`curl -I -v https://example.com`，看 TCP 连上没、TLS 握手成没、HTTP 状态码是多少。返回 502/504 说明已经到 Nginx 了，问题在后端；连接被拒说明后端服务没起。

第五，上服务端。先看服务自己：`ss -tlnp | grep 443` 确认在监听；`systemctl status nginx`、`docker ps` 看容器状态；`tail -f /var/log/nginx/error.log`。再看防火墙：`iptables -L -n`、`firewall-cmd --list-all`，云厂商还要看安全组。最后才上 `tcpdump -i eth0 port 443 -nn -w /tmp/web.pcap` 抓包回 Wireshark 分析。

一套下来基本能定位：本机→DNS→网络路径→端口→应用→服务端日志/防火墙。

</details>

<details>
<summary>Q8：tcpdump 常用用法？</summary>

**答：**

结论：tcpdump 是命令行抓包神器，核心是"选对网卡、写对过滤表达式、存下来用 Wireshark 看"。

最常用的几个例子：

```bash
# 抓 eth0 上 80 端口的包，-n 不解析域名，-nn 连端口也不解析成服务名
tcpdump -i eth0 -nn port 80

# 只抓和某台主机的来往包
tcpdump -i any -nn host 1.2.3.4

# 组合：来自某主机、访问 22 端口
tcpdump -i eth0 -nn src host 192.168.1.10 and dst port 22

# 只抓 TCP 握手包（看 SYN/ACK）
tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-syn != 0'

# 存成文件，回头用 Wireshark 打开分析
tcpdump -i eth0 -nn -s 0 -w /tmp/web.pcap port 443

# 看文件内容
tcpdump -r /tmp/web.pcap -nn
```

几个关键参数：`-i any` 抓所有网卡；`-nn` 强烈建议加，不然慢还会把自己 DNS 打爆；`-s 0` 抓完整包（默认只抓前 68 字节）；`-c 100` 抓够 100 个就停；`-w` 存盘，`-r` 读回来。

过滤表达式用 BPF 语法，可以用 `and/or/not` 组合 `host/net/port/src/dst/protocol`。线上排查 502、端口不通、TLS 握手失败，最有效的办法就是在 Nginx 那台和后端那台同时抓包，对着看 SYN 到哪去了、RST 是谁发的。复杂协议解析交给 Wireshark：`tcp.analysis.retransmission`、`tcp.stream` 跟一条流，比肉眼看文本高效得多。

</details>
