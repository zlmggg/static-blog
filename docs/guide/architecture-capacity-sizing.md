# 容量估算与服务器选型清单

::: tip 本篇定位
回答一个最实际的问题：**这个业务该买几台机器、每台买多大配置？** 从日 PV 出发，一步步算出峰值 QPS，再按各层单机的"经验承载能力"倒推机器数量，最后给出日 PV 1 万 / 10 万 / 100 万 / 1000 万 / 1 亿五档的完整配置清单。所有数字都是业界经验起点，**必须用压测校验**，不能照抄上线。配套：[架构设计方法论](#合并资料)、[高可用与容灾](#合并资料)。
:::

## 一、先把这些概念算清楚

小白类比：估算饭馆要多少座位，得先知道**每天来多少人（PV）、最忙那一小时挤进来多少人（峰值 QPS）、同时坐下来点菜的有几桌（并发）**。服务器同理。

| 指标 | 含义 | 怎么估 |
|---|---|---|
| PV（页面浏览量） | 一天页面被打开多少次 | 业务方给 / 拍脑袋起步 |
| UV（独立访客） | 一天多少个不同的人来 | 通常 UV ≈ PV 的 1/3 ~ 1/10 |
| QPS | 每秒查询数（读为主） | **峰值 QPS = 日 PV ÷ 86400 × 峰值系数** |
| TPS | 每秒事务数（写为主） | 一般远小于 QPS，读写比常见 5:1 ~ 10:1 |
| 并发在线数 | 同时正在操作的用户数 | ≈ 日活 × 同时在线比例（常见 5%~10%） |
| 数据量 | 一年产生多少数据 | 单条记录大小 × 日增量 × 天数 |
| 带宽 | 网络出口要多大 | 峰值 QPS × 单请求响应字节 |

### 1.1 峰值 QPS 换算公式

一天的访问从不均匀——大部分集中在白天高峰的 2~4 小时。业界常用简化：

```
平均 QPS = 日 PV ÷ 86400
峰值 QPS ≈ 平均 QPS × 峰值系数（经验 50~100）
```

> 峰值系数取 50 的含义：全天约 5% 的流量挤在 1 小时内（≈3600 秒），即 日PV×5%÷3600 ≈ 日PV÷72000。大促/突发场景要再乘 2~3 倍。

| 日 PV | 平均 QPS | 峰值 QPS（×50） | 大促峰值（×2） |
|---|---|---|---|
| 1 万 | 0.1 | ~6 | ~12 |
| 10 万 | 1.2 | ~60 | ~120 |
| 100 万 | 11.6 | ~580 | ~1200 |
| 1000 万 | 116 | ~5800 | ~1.2 万 |
| 1 亿 | 1157 | ~5.8 万 | ~12 万 |

## 二、各层单机承载经验值

⚠️ **这些是"起点经验值"，业务逻辑复杂度影响极大**：一个空接口和一个要 JOIN 三张表的接口，QPS 差 10 倍。上线前务必压测。

### 2.1 接入 / Web 层

| 组件 | 单机经验承载 | 说明 |
|---|---|---|
| Nginx 静态 Web | 3 万~5 万 QPS | 纯静态小文件，瓶颈主要是连接数和带宽 |
| Nginx 反向代理/网关 | 1 万~3 万 QPS | 转发+日志+限流，比纯静态低 |
| LVS / DPVS（四层） | 10 万+ QPS | 内核态转发，性能极高，做大流量入口 |

### 2.2 应用层（业务代码）

| 技术栈 | 单机经验承载（简单接口） | 复杂业务接口 |
|---|---|---|
| Java / Spring Boot（4C8G） | 800~1500 QPS | 300~500 QPS |
| Go（4C8G） | 3000~8000 QPS | 1000~2000 QPS |
| Node.js（4C8G） | 1000~2000 QPS | 看异步化程度 |

> **CPU 核数与 QPS 经验关系**：Java 业务接口大致 **1 核 ≈ 200~400 QPS**（压到 70% 利用率）；Nginx 静态 **1 核 ≈ 5000~10000 QPS**。应用层加 CPU 基本线性，但要同步加内存（线程栈、GC）。

### 2.3 数据层

| 组件 | 单机经验承载 | 容量建议 |
|---|---|---|
| MySQL（主库） | 写 TPS 500~2000；读 QPS 2000~5000 | 单表建议 < 2000 万行 / < 50GB；超过就分库分表 |
| MySQL（从库） | 读 QPS 3000~8000 | 读多写少就多加从库做读写分离 |
| Redis（单实例） | 8 万~12 万 QPS | 单实例内存建议 < 10GB（大了 fork 会阻塞）；数据量大上 Cluster |
| Kafka（单 broker） | 写入 5 万~10 万条/秒 | 吞吐靠分区数和 broker 数水平扩展 |

### 2.4 内存 / 连接 / 磁盘 / 带宽经验

| 维度 | 经验规则 |
|---|---|
| **JVM 内存** | `-Xmx` 设为物理内存的 50%~70%，留给堆外、Metaspace、OS page cache；不要把 16G 全给堆 |
| **连接数** | 每个 TCP 连接约占 4KB 内核缓冲；Nginx `worker_connections` 调大到数万；应用连接池（DB）大小别盲目开大，MySQL `max_connections` 通常 500~2000 封顶 |
| **磁盘 IOPS** | 机械盘 ~100~200 IOPS；SATA SSD ~1万；NVMe SSD ~5万~10万。数据库、Redis 持久化、Kafka 落盘必须 SSD/NVMe |
| **磁盘容量** | 按数据量 ×3 年增长预留，日志盘和数据盘分开；MySQL 留 binlog + 备份空间 |
| **带宽** | `带宽(Mbps) = 峰值QPS × 单请求平均响应字节 × 8 ÷ 1024 ÷ 1024`；静态资源走 CDN，源站带宽只回源 |

> 带宽例子：峰值 5000 QPS，接口平均响应 10KB，则出网 ≈ 5000 × 10KB × 8 ≈ 400 Mbps，按 500M 带宽买。静态图片走 CDN 后源站带宽可降一个数量级。

## 三、五档规模配置清单

下表按"峰值 QPS ÷ 单机经验承载"向上取整，并加 **N+1 冗余**（挂一台不影响）和 **3 年增长预留**（约 ×1.5~2）。假设：读写比 5:1、业务为中等复杂度 Web 后端、Linux 云服务器。

### 3.1 日 PV 1 万（初创 / 内部系统）

| 层 | 数量 | 单台配置 | 说明 |
|---|---|---|---|
| Nginx 接入 | 1~2 台 | 2C4G | 可与应用混部 |
| 应用服务 | 2 台 | 2C4G | 主备/双活 |
| MySQL | 1 主 1 从 | 4C8G / 100G SSD | 必做主从备份 |
| Redis | 1 台 | 2C4G（可混部） | 数据少可先不用 |
| MQ | 0 | — | 量小先不上，用同步 |
| **合计** | **~4 台** | | 可先 2 台起步 |

### 3.2 日 PV 10 万（小型创业产品）

| 层 | 数量 | 单台配置 | 说明 |
|---|---|---|---|
| Nginx 接入 | 2 台 | 2C4G（Keepalived VIP） | 见 [LVS+Keepalived](/services/web/lvs-keepalived) |
| 应用服务 | 2~3 台 | 4C8G | 无状态，前面 Nginx 轮询 |
| MySQL | 1 主 1 从 | 8C32G / 500G SSD | 读写分离雏形 |
| Redis | 3 台（哨兵） | 4C8G | 或 1 主 1 从 + 1 哨兵 |
| MQ | 0~3 台 | 4C8G | 有异步需求再上 Kafka |
| **合计** | **7~9 台** | | |

### 3.3 日 PV 100 万（成长期业务）

| 层 | 数量 | 单台配置 | 说明 |
|---|---|---|---|
| LVS + Nginx 接入 | 2~3 台 | 4C8G | 四层+七层分层 |
| 应用服务 | 4~6 台 | 8C16G | 按 ~500 QPS/台，580 峰值需 ~2 台，留冗余 |
| MySQL | 1 主 2 从 | 16C64G / 1T SSD | 读写分离，考虑垂直拆分 |
| Redis | 3~5 台 | 8C32G | 哨兵或小 Cluster |
| Kafka | 3 台 | 8C32G / 1T SSD | 削峰、异步解耦 |
| **合计** | **~15~18 台** | | |

### 3.4 日 PV 1000 万（中型平台）

| 层 | 数量 | 单台配置 | 说明 |
|---|---|---|---|
| LVS/DPVS + Nginx 网关 | 4 台 | 8C16G | 接入层集群 |
| 应用服务 | 12~20 台 | 16C32G | 微服务拆分后按服务独立扩 |
| MySQL | 6~8 台 | 32C128G / 2T NVMe | 分库分表 + 多主从，见 [MySQL 进阶](/services/database/mysql/01-理论) |
| Redis Cluster | 6~9 台 | 16C64G | 分片集群 |
| Kafka | 5~7 台 | 16C64G / 2T NVMe | 多分区多副本 |
| **合计** | **~35~50 台** | | |

### 3.5 日 PV 1 亿（大型 / 头部业务）

| 层 | 数量 | 单台配置 | 说明 |
|---|---|---|---|
| DPVS + 网关集群 | 8~12 台 | 16C32G | 接入层多机房 |
| 应用服务 | 40~80 台 | 16C32G | 按微服务分别扩缩 |
| MySQL | 20~30 台 | 32C128G / 4T NVMe | 分库分表、多集群、异地 |
| Redis Cluster | 15~20 台 | 32C128G | 大集群+多副本 |
| Kafka | 10~15 台 | 32C128G / 4T NVMe | 高吞吐多机房 |
| 对象存储/CDN | 云服务 | — | 图片视频全走 OSS+CDN |
| **合计** | **~100~160 台** | | 应考虑容器化弹性伸缩 |

> 1000 万 PV 以上强烈建议容器化：参考 [K8s 架构与集群](/services/container/kubernetes/01-理论)，用 HPA 自动伸缩代替固定买机器。

## 四、3 年增长预留与压测校验

| 事项 | 做法 |
|---|---|
| **增长预留** | 按业务年增长率（常见 50%~100%）算 3 年后容量，机器数量再乘 1.3~1.5；数据库按 3 年数据量规划分库分表时机 |
| **余量 Headroom** | 日常 CPU 水位控制在 60%~70%，留 20%~30% 应对突发和单台宕机接管 |
| **压测校验** | 上表只是"估"，必须压测：单台应用压到 CPU 70% 时的真实 QPS、MySQL 慢查询拐点、Redis 大 key 延迟、MQ 积压 |
| **压测后修正** | 若实测单机 QPS 只有经验值一半，就把机器数 ×2；这比拍脑袋可靠得多 |
| **观测兜底** | 上线后用 Prometheus 看实际水位，持续修正：见[容量规划与灾备](./sre-capacity-dr)、[SLO](./monitor-slo) |

#### 一、高可用架构演进路线

小白类比：高可用就是"别把鸡蛋放一个篮子"。篮子从 1 个 → 2 个 → 分散到两个城市 → 两个城市都能同时做菜。每多一份冗余，成本翻一倍，但停服时间趋近于零。

| 模式 | 可用性 | 成本 | RTO | RPO | 适用场景 |
|---|---|---|---|---|---|
| **单点** | 无（挂了就全停） | 最低 | 小时级 | 看运气 | 个人项目、测试环境 |
| **主备双机（Active-Standby）** | ~99.9% | 低（备机闲置） | 分钟级 | 秒~分钟（取决于同步） | 小业务入门、DB 主从 |
| **主主 / 双活（同机房）** | ~99.95% | 中（两台都跑业务） | 秒级 | 接近 0（同步） | 中等业务、网关/应用层 |
| **集群（多副本）** | ~99.95%~99.99% | 中高 | 秒级 | 接近 0 | 微服务无状态层、Redis Cluster |
| **两地三中心** | ~99.99% | 高 | 分钟级 | 分钟级 | 金融、对机房级故障有要求 |
| **异地多活** | ~99.995%+ | 很高 | 秒级 | ≈0 | 头部互联网、双11 级别 |

> **RTO / RPO 是什么**（见下节）：演进的本质，就是花更多钱把 RTO（恢复要多久）和 RPO（最多丢多少数据）压得更小。

#### 二、RTO / RPO 与可用性等级

| 概念 | 含义 | 大白话 | 达标手段 |
|---|---|---|---|
| **RTO**（Recovery Time Objective） | 故障后恢复服务的目标时间 | 挂了之后多久能恢复 | 自动故障转移、无状态多副本、预热 |
| **RPO**（Recovery Point Objective） | 恢复后最多能容忍丢多久的数据 | 最多丢多久的数据 | 同步复制（RPO≈0）、半同步、定期备份 |

| 可用性 | 年允许停机时间 | 大约对应 |
|---|---|---|
| 99% | 3.65 天 | 单点 |
| 99.9% | 8.76 小时 | 主备双机 |
| 99.95% | 4.3 小时 | 双活/集群 |
| 99.99% | 52.6 分钟 | 两地三中心 |
| 99.999% | 5.26 分钟 | 异地多活 |

> 可用性每多一个 9，成本大致翻一倍。**别盲目追求 5 个 9**——内部系统 99.9% 往往就够了。

#### 三、分层负载均衡：DNS → 四层 → 七层

大流量不能只靠一个 Nginx，要**层层分流**，每一层都自己是高可用集群：

| 层级 | 组件 | 工作在哪层 | 作用 | 高可用做法 |
|---|---|---|---|---|
| 第 1 层 | DNS（智能解析 / GSLB） | 应用层 | 按地域/运营商把流量导到不同机房 | 多机房解析、健康检查切流 |
| 第 2 层 | LVS / DPVS | 四层（TCP/UDP，按 IP+端口） | 海量并发入口，内核态转发性能极高 | LVS 主备 + Keepalived VIP，见 [LVS+Keepalived](/services/web/lvs-keepalived) |
| 第 3 层 | Nginx / 网关（APISIX） | 七层（按 URL/Header） | 路由、限流、鉴权、SSL 卸载 | 多实例 + 上面 LVS 转发，见 [Nginx](/services/web/nginx/01-理论)、[APISIX](/guide/data#合并资料) |
| 第 4 层 | 应用服务 | 业务层 | 无状态实例，随便加机器 | 前面网关轮询，实例挂了自动摘除 |

> 口诀：**DNS 选机房 → LVS 扛大并发 → Nginx 做路由 → 应用随便扩**。小流量可以直接用 Nginx、跳过多层；但量大了必须分层，否则单点网卡/CPU 先成瓶颈。

#### 四、无状态 vs 有状态

| 类型 | 特点 | 高可用策略 |
|---|---|---|
| **无状态组件**（应用、网关、Nginx） | 不在本地存会话，请求随便发给哪台都行 | **直接水平加副本**，前面挂负载均衡，挂一台无感。会话放 Redis 共享 |
| **有状态组件**（MySQL、Redis、MQ） | 自己存数据，换机器很麻烦 | 需要主从复制 + 故障转移，不能简单加机器 |

##### 4.1 有状态组件高可用清单

| 组件 | 高可用方案 | 故障转移 | 关键点 |
|---|---|---|---|
| **MySQL** | 主从复制 + 半同步；MGR（组复制）或 Orchestrator/MHA 自动切主 | MHA/Orchestrator 自动提升从库 | 防止脑裂、VIP 漂移、应用改连接串。详见 [MySQL 进阶与高可用](/services/database/mysql/01-理论) |
| **Redis** | 主从 + 哨兵（Sentinel）；大数据量上 Cluster 分片 | 哨兵自动选新主 | 主从切换期间可能丢少量写（异步复制）。详见 [Redis](/services/database/redis/01-理论) |
| **Kafka** | 多 Broker + Topic 多副本（`acks=all`） | Leader 挂了 Controller 选新 Leader | 副本数 ≥3、min.insync.replicas 保证不丢。详见 [Kafka](/guide/data#合并资料) |

#### 五、故障切换与脑裂防护

**脑裂（Split-Brain）**：主备之间的心跳线断了，备机以为主机挂了，自己也起来当主——结果两个主同时写一份数据，数据就乱了。

| 防护手段 | 做法 |
|---|---|
| **仲裁节点（Quorum）** | 引入第三方仲裁（如 VIP/表决服务器），少数派那侧自动下台，不能自己说了算 |
| **双心跳线** | 同时用两条独立链路做心跳，一条断了不误判 |
| **Fencing（隔离）** | 切主时强制把旧主"踢下去"（如 STONITH 断电/关端口），防止它还在写 |
| **资源锁** | 旧主启动前先抢锁，抢不到就不提供服务 |

> 主备切换不是"脚本跑一下"那么简单：切之前要确认旧主真的挂了（脑裂防护），切之后要校验数据一致性、把连接切过去。**没演练过的故障切换等于没有**——定期做故障演练，见[混沌工程](/guide/sre-incident#合并资料)。

#### 六、备份 3-2-1 原则

再高的架构也得留备份兜底。业界黄金法则 **3-2-1**：

| 数字 | 含义 |
|---|---|
| **3** | 至少保留 **3 份**数据（生产 + 2 份备份） |
| **2** | 备份放在 **2 种不同介质**上（如本地盘 + 对象存储） |
| **1** | 其中 **1 份异地**存放（防机房火灾/地震） |

补充实践：备份要**定期做恢复演练**（能恢复的备份才算备份）、敏感数据备份要加密、MySQL 用 `mysqldump`/`xtrabackup` 定期全量 + binlog 增量（见 [MySQL 备份恢复](/services/database/mysql/01-理论)）。

#### 一、架构师要同时达成的六个目标

小白类比：盖房子，不能只追求"结实"（不然成本上天），也不能只追求"便宜"（不然地震就塌）。架构就是在**结实、快、能加房间、防火、省钱、能监控**这六件事之间找平衡。

| 目标 | 一句话定义 | 核心手段 | 典型衡量指标 |
|---|---|---|---|
| 高可用（HA） | 系统出故障的时间尽量少 | 冗余、故障转移、无状态化、降级 | 可用性 SLA（如 99.95%）、RTO/RPO |
| 高性能 | 响应快、吞吐大 | 缓存、异步、连接池、读写分离、SQL/索引优化 | 接口 P99 延迟、QPS/TPS |
| 可扩展 | 业务涨了能"加机器"就扛住 | 无状态水平扩展、分库分表、微服务拆分 | 扩容后线性提升比、扩缩容耗时 |
| 安全 | 数据不被偷、不被篡改、不被拖库 | 认证鉴权、加密、最小权限、审计、WAF | 安全事件数、漏扫通过率 |
| 可控成本 | 不过度设计、钱花在刀刃上 | 按规模选型、弹性伸缩、资源利用率优化 | 单 QPS 成本、资源空闲率 |
| 可观测 | 出问题能快速看见、定位 | 指标/日志/链路三件套、告警、SLO | 平均定位时间 MTTR、告警有效率 |

> **关键认知**：这六个目标永远互相冲突。比如"为了高可用做多副本"会增加"成本"；"为了性能把数据放缓存"会牺牲"一致性/安全"。架构设计的本质不是"全都要"，而是**说清楚你放弃了什么、为什么**。

#### 二、架构演进：单体 → 分层 → SOA → 微服务 → 云原生

没有最好的架构，只有**最适合当前团队规模和业务阶段**的架构。演进的核心驱动力永远是：**人变多了、代码库变大了、流量变高了**。

```mermaid
flowchart LR
    A["单体架构<br>All in one"] --> B["分层架构<br>MVC 三层"]
    B --> C["SOA<br>面向服务/ESB"]
    C --> D["微服务<br>独立部署"]
    D --> E["云原生<br>容器+编排+ServiceMesh"]
    style E fill:#2d5a2d,color:#fff
```

| 阶段 | 适用团队/规模 | 优点 | 缺点 / 痛点 | 什么时候该往下一阶段走 |
|---|---|---|---|---|
| **单体** Monolith | 1~5 人初创、日活几千 | 开发部署简单、调试方便、没有分布式开销 | 代码库一大就编译慢、牵一发动全身、技术栈锁定、单点故障影响全局 | 代码库多人并行开发频繁冲突、一次发布要全量回归 |
| **分层**（经典三层） | 5~20 人、日活几万 | 职责清晰（表现/业务/数据）、可按层优化、便于分工 | 还是一个部署包，层间调用是进程内调用，无法独立扩展某一层 | 只有某一层（如应用层）扛不住，想单独扩容它 |
| **SOA** | 20~100 人、有多个业务线 | 服务复用、统一 ESB 总线、系统集成 | ESB 是重量级单点、耦合仍重、治理复杂 | ESB 成为瓶颈和单点、想让服务真正独立部署 |
| **微服务** Microservices | 100+ 人、多团队、日活百万级 | 服务独立部署/扩缩/技术选型、故障隔离、团队自治 | 分布式复杂度爆炸（网络、一致性、运维成本）、链路长 | 团队超过两个 Pizza Team、发布互相排队 |
| **云原生** Cloud Native | 大规模、多环境、追求弹性与交付效率 | 容器化一致环境、K8s 自动编排、弹性伸缩、声明式 API、可观测 | 学习曲线陡、平台本身也要运维、小团队用不动 | 已经有十几个微服务、环境管理和发布成为瓶颈 |

> **反模式提醒**：业务还在日 PV 10 万级别就上来一整套微服务 + K8s + ServiceMesh，是典型的**过度设计**——分布式带来的故障和运维成本，远超它能带来的收益。先单体跑通、出现真实痛点再拆。

#### 三、数据一致性与通信模式

##### 3.1 CAP 取舍

分布式系统不可能同时完美满足三者，必须**二保一、牺牲一个**：

| 维度 | 含义 | 大白话 |
|---|---|---|
| C（Consistency） | 一致性：所有节点同一时刻看到相同数据 | 大家看到的数一模一样 |
| A（Availability） | 可用性：每个请求都能拿到非错响应 | 随时来请求都有人理 |
| P（Partition tolerance） | 分区容忍：网络断成两截还能跑 | 机房网线断了也不彻底死 |

**网络分区在现实中必然发生（P 必须保）**，所以实际是在 C 和 A 之间选：

| 取舍 | 选它意味着 | 典型代表 | 适用场景 |
|---|---|---|---|
| CP | 分区时拒绝部分请求保一致 | ZooKeeper、etcd、HBase | 配置中心、分布式锁、库存扣减这类"错了更糟"的 |
| AP | 分区时先可用，数据稍后对齐 | Cassandra、DynamoDB、Eureka（早期） | 购物车、Feed 流、社交点赞这类"短暂不一致能忍"的 |
| CA | （单机/单节点才谈得上） | 传统单机 MySQL | 没做分布式时天然近似 CA |

##### 3.2 BASE 与强 / 最终一致性

BASE 是 AP 路线的落地哲学：**基本可用（Basically Available）、软状态（Soft state）、最终一致（Eventually consistent）**。

| 一致性模型 | 含义 | 代价 | 典型场景 |
|---|---|---|---|
| 强一致性 | 写完立刻能读到最新值 | 性能低、要同步等所有副本 | 账户余额、扣库存、转账 |
| 最终一致性 | 写完允许短暂旧，副本后台对齐 | 业务要容忍短暂不一致 | 浏览数、点赞数、订单状态同步 |
| 读己之写 / 会话一致性 | 我自己写完自己立刻能读到 | 折中 | 发帖后自己立刻看到 |

##### 3.3 同步 vs 异步通信

| 维度 | 同步（HTTP/RPC 直连） | 异步（消息队列 MQ） |
|---|---|---|
| 调用方式 | 调用方阻塞等响应 | 发完消息就走，结果 later |
| 优点 | 简单、实时、调用方马上知道成败 | 削峰填谷、解耦、容错好、下游慢不拖垮上游 |
| 缺点 | 强耦合、下游拖慢会拖垮上游、级联失败 | 不能立刻拿结果、要处理消息重复/丢失、链路不直观 |
| 适用 | 下单后立刻要扣减结果 | 下单后发积分、发短信、推统计、日志采集 |

> 经验：**能异步就异步**。一个写操作里，主链路（扣钱扣库存）走同步，周边动作（通知、积分、风控、报表）全部丢 MQ 异步化，是高并发系统的标配。

#### 四、高并发三板斧：限流 / 降级 / 熔断

小白类比：饭馆爆满时——**限流**（门口发号，超了不接待新客）、**降级**（贵宾室暂停供水果，先保住主力菜品）、**熔断**（某道菜的后厨一直出问题，干脆先不接这道菜的单，等它恢复）。三者都是为了**保住核心链路，牺牲边角功能**。

| 手段 | 解决什么 | 常见实现 | 关键参数 |
|---|---|---|---|
| **限流** | 流量超过系统承载，直接挡掉多余请求 | 计数器、滑动窗口、漏桶、令牌桶；网关层（Nginx limit_req / Sentinel） | 阈值 QPS、拒绝策略（直接拒/排队） |
| **降级** | 非核心功能出问题或压力大时主动关掉 | 开关配置中心、页面静态化、返回兜底数据 | 降级开关、兜底返回值 |
| **熔断** | 下游持续失败时，快速失败不再调用，给下游喘息 | 熔断器（Closed→Open→Half-Open）；Sentinel/Resilience4j | 错误率阈值、熔断时长、半开探测次数 |

三板斧之外，还有六个配套保护，缺一个都可能在高压下雪崩：

| 配套机制 | 作用 | 一句话原则 |
|---|---|---|
| **资源隔离** | 线程池/信号量隔离，防止一个慢接口占满全部线程 | 不同业务用不同线程池，互不拖累（舱壁模式） |
| **超时 Timeout** | 调用必须有超时，绝不无限等 | 每次 RPC/HTTP 调用都设超时，且内层 < 外层 |
| **重试 Retry** | 偶发失败自动重试 | 只重试幂等操作、有限次、加退避，配熔断防止重试风暴 |
| **幂等 Idempotency** | 同一请求重复执行结果一致 | 用唯一请求号/业务主键去重，否则重试会重复扣钱 |
| **回压 Backpressure** | 下游处理不过来时反向告诉上游慢点 | MQ 消费限速、TCP 接收窗口，别把内存撑爆 |
| **缓存** | 把读请求挡在数据库前面 | 多级缓存（本地 + Redis），配过期与击穿/穿透/雪崩防护 |

> 这一块的组件落地见 [Spring Cloud 全家桶（Sentinel）](/guide/data#合并资料) 与 [Kafka](/guide/data#合并资料)。

#### 五、架构设计流程（从需求到评审）

一套可复用的六步流程，避免"上来就画框框"：

| 步骤 | 做什么 | 产出物 | 关键问题 |
|---|---|---|---|
| 1. 需求澄清 | 搞清楚业务要做什么、规模多大 | 需求文档、用户故事 | 这功能给谁用？日活/订单量大概多少？ |
| 2. 定关键非功能指标 | 把"要快/要稳"变成数字 | NFR 表：QPS、延迟 P99、可用性 RTO/RPO、数据量级 | 能容忍多慢？能容忍丢多少数据？ |
| 3. 技术选型 | 据规模选合适组件，不炫技 | 选型对比表（含备选方案） | 单机够不够？要不要缓存/分库？成熟度还是性能优先？ |
| 4. 画架构图 | 分层图、时序图、部署图 | C4 / 架构图、关键链路时序 | 请求从进来到落库经过哪几层？ |
| 5. 容量评估 | 算要多少台机器、多大带宽 | 容量清单（见[容量估算](./architecture-capacity-sizing)） | 峰值 QPS 多少？单机扛多少？留多少余量？ |
| 6. 评审与演进 | 拉上 SRE/DBA/安全一起挑刺 | 评审纪要、风险清单、落地排期 | 单点在哪？怎么回滚？故障演练过吗？ |

> **流程要点**：第 2 步（把非功能指标量化）最容易被跳过，却是后面所有选型和容量计算的输入。没有数字，"高可用"只是一句口号。
