# MySQL 01 · 服务理论

> 四篇制：[01 理论](./01-理论) · [02 部署](./02-部署) · [03 功能](./03-功能) · [04 实战](./04-实战)
> 本篇讲"MySQL 内部是怎么运转的"：一条 SQL 怎么被执行、数据怎么保证不丢不乱、索引为什么快、并发怎么不打架。把这些想明白，后面的 EXPLAIN、慢查询、主从延迟都不是玄学。动手装库直接去 [02 部署](./02-部署)。

## 一、它是什么：关系型数据库

MySQL 是最流行的开源**关系型数据库管理系统（DBMS）**。"关系型"的核心是把数据组织成**二维表**：一行是一条记录，一列是一个字段，表与表之间用主键、外键建立关系，用 **SQL** 操作。它最大的卖点是**事务**——遵循 ACID，保证一组操作"要么全做、要么全不做"，这在钱、订单这类业务上是刚需。

几个层次先分清：

- **数据库（DB）**：有组织、可共享的数据集合本身。
- **数据库管理系统（DBMS）**：管理数据库的软件，MySQL/MariaDB/Oracle 都是。
- **数据库系统（DBS）**：DB + DBMS + 应用 + 管理员（DBA）的整体。

**MySQL 与 MariaDB**：MariaDB 是 MySQL 原作者主导的开源分支，命令、配置、SQL 基本兼容，开源更彻底。MySQL 主流是 8.0（8.4 为 LTS），MariaDB 11.4 为 LTS。本站实验环境用 MariaDB 11.4，下文两者命令一致处合并说明、差异处单独标注。

### 三大范式：表为什么这么设计

范式是建表的规范，目的是**减少冗余、避免增删改异常**：

| 范式 | 核心要求 | 通俗理解 |
|---|---|---|
| 1NF | 字段不可再分 | 一个格子不能塞"电话1,电话2" |
| 2NF | 非主属性完全依赖主键 | 联合主键时，字段不能只依赖主键的一部分 |
| 3NF | 消除传递依赖 | 学生表里不该同时存"学院编号+学院名+学院电话"，学院信息单独建表 |

工程上做到 3NF 通常就够；有时为查询性能**故意反范式**（如订单里冗余存商品快照名），这是规范与性能的权衡，不是错误。

## 二、体系结构：一条 SQL 的一生

MySQL 是**单进程多线程**的数据库。一条查询从发出到返回，走过这样一条链路：

```mermaid
flowchart LR
    A["客户端"] --> B["连接器<br/>认证/授权"]
    B --> C["解析器<br/>词法/语法分析"]
    C --> D["优化器<br/>选索引/定执行顺序"]
    D --> E["执行器<br/>调存储引擎接口"]
    E --> F["InnoDB<br/>读写数据页"]
    F --> G["返回结果"]
```

逻辑上分四层：

| 层 | 组件 | 职责 |
|---|---|---|
| 连接层 | 连接池、线程处理 | 认证、权限校验、为每个连接分配线程 |
| 服务层 | SQL 接口、解析器、优化器 | 解析 SQL、生成执行计划（8.0 已移除查询缓存） |
| 存储引擎层 | InnoDB、MyISAM 等 | **插件式**，负责数据的存储和提取 |
| 文件系统层 | 数据文件、日志 | 落盘（redo/undo/binlog、表空间） |

记住这条链路，后面的索引、EXPLAIN、慢查询都是在某个环节做文章：**优化器选错索引**就在 EXPLAIN 里看，**执行器扫描太多行**就在 rows 里看，**引擎层 IO 慢**就看 Buffer Pool 命中率。查询缓存在 8.0 被移除，是因为它"表一更新就整块失效"，命中率低、维护成本高，弊大于利。

## 三、InnoDB 为什么可靠：WAL 与三大日志

InnoDB 是默认存储引擎，它支持事务和崩溃恢复的底层原因，是**先写日志再写数据（WAL，Write-Ahead Logging）**。

### 3.1 InnoDB vs MyISAM

| 对比项 | InnoDB（默认） | MyISAM |
|---|---|---|
| 事务 | 支持 ACID | 不支持 |
| 锁粒度 | 行锁，并发高 | 表锁 |
| 外键 | 支持 | 不支持 |
| 索引结构 | 聚簇索引（数据与主键一起存） | 非聚簇 |
| 崩溃恢复 | 支持（redo 重放） | 差 |
| 适用 | OLTP 通用（默认选它） | 以读为主的老应用 |

### 3.2 内存结构：Buffer Pool 是性能命门

| 区域 | 作用 |
|---|---|
| **Buffer Pool** | 最大的内存区，缓存数据页和索引页，读写先走这里，**命中率决定性能** |
| Change Buffer | 缓存对非唯一二级索引的修改（写缓冲） |
| Log Buffer | 缓存 redo log，再刷盘 |
| Adaptive Hash Index | 自动为热点页建哈希索引 |

为什么 Buffer Pool 这么关键？因为磁盘 IO 比内存慢几个数量级。InnoDB 把热数据缓存在 Buffer Pool，读命中就不碰磁盘；写也是先改内存页（变成"脏页"），由后台线程异步刷盘。生产上 `innodb_buffer_pool_size` 通常设为物理内存的 50%~75%，就是为了让尽量多的热数据留在内存。

### 3.3 三大日志各管什么

| 日志 | 层 | 作用 | 写法 |
|---|---|---|---|
| **redo log** | InnoDB 引擎层 | 崩溃恢复，保证**持久性** | 物理日志，**循环写**（固定大小覆盖） |
| **undo log** | InnoDB 引擎层 | 回滚 + MVCC，保证**原子性** | 记录修改前的旧值 |
| **binlog** | Server 层（所有引擎） | 复制、归档、时间点恢复 | 逻辑日志，**追加写** |

- **redo log**：修改数据时先把"某页某偏移改成什么"记进 redo log。即使脏页还没刷盘就宕机，重启也能用 redo log 把已提交的修改重放回来——这就是"提交后不丢"的底气。
- **undo log**：记录修改前的数据，事务回滚时用它还原；同时它串成"版本链"，支撑 MVCC（见下节）。
- **binlog**：记录所有更改，用于主从复制和恢复到某个时间点。三种格式 STATEMENT（记 SQL）/ ROW（记行变更，**默认推荐**）/ MIXED。

**redo 和 binlog 为什么都要有？** redo 是引擎层的物理日志、循环写、只管崩溃恢复；binlog 是 Server 层的逻辑日志、追加写、管复制和归档。两者通过**两阶段提交**（先 prepare 写 redo → 写 binlog → commit）保证一致，避免"redo 恢复了但 binlog 没有"导致主从数据不一致。

## 四、事务与 MVCC：并发怎么不打架

### 4.1 ACID 各靠什么

| 特性 | 含义 | 实现 |
|---|---|---|
| 原子性 | 失败全部回滚 | undo log |
| 一致性 | 事务前后数据完整 | 其他三者共同保证 |
| 隔离性 | 并发互不干扰 | 锁 + MVCC |
| 持久性 | 提交后永久生效 | redo log |

### 4.2 并发的三个问题与四种隔离级别

并发事务会引发：**脏读**（读到别人没提交的）、**不可重复读**（同一行两次读结果不同，被别人 UPDATE）、**幻读**（同一条件两次查行数不同，被别人 INSERT/DELETE）。四种隔离级别就是在这三者与并发度之间取舍：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 RU | 可能 | 可能 | 可能 |
| 读已提交 RC（Oracle 默认） | 避免 | 可能 | 可能 |
| **可重复读 RR（InnoDB 默认）** | 避免 | 避免 | Next-Key Lock 很大程度避免 |
| 串行化 Serializable | 避免 | 避免 | 避免（读也加锁，并发最低） |

### 4.3 MVCC：读不加锁的秘密

**MVCC（多版本并发控制）** 让普通 SELECT 在 RC/RR 下**不加锁、读快照**，读写互不阻塞——这是 InnoDB 高并发的关键。它由三部分构成：

1. **隐藏列**：每行有 `DB_TRX_ID`（最后修改它的事务 ID）、`DB_ROLL_PTR`（指向 undo log 旧版本）。
2. **undo log 版本链**：每次修改把旧值写入 undo log，用 roll_ptr 串成链。
3. **ReadView（读视图）**：生成时记录当前活跃（未提交）事务 ID 列表。

读的时候沿版本链找第一个"对本 ReadView 可见"的版本（即该版本的事务已提交）。**RC 与 RR 的本质区别**就在 ReadView 的生成时机：RC **每次** SELECT 都生成新 ReadView，所以能看到别人刚提交的（不可重复读）；RR **第一次** SELECT 生成后全程复用，所以整个事务看到的数据一致。

## 五、锁：行锁加在索引上

| 维度 | 类型 |
|---|---|
| 粒度 | 全局锁、表级锁、行级锁 |
| 模式 | 共享锁 S（读，可共存）、排他锁 X（写，互斥） |

行级锁（InnoDB）有三种形态：**记录锁**（锁某条索引记录）、**间隙锁 Gap**（锁记录之间的间隙，防插入）、**临键锁 Next-Key**（记录锁+前面的间隙，RR 默认，左开右闭，用于防幻读）。

::: warning 最关键的认知
**行锁是加在索引上的**。如果 UPDATE/DELETE 的条件**没走索引**，InnoDB 会锁住全表所有行（等效表锁）。这就是"一条没加索引的更新把整张表卡死"的根因——排障时先看条件有没有走索引。
:::

**死锁**：两个事务互相持有对方需要的锁。InnoDB 有死锁检测（wait-for graph），发现后自动回滚代价较小的那个。用 `SHOW ENGINE INNODB STATUS\G` 的 LATEST DETECTED DEADLOCK 段看。避免手段：统一加锁顺序、缩短事务、保证走索引。

## 六、索引为什么快：B+ 树

索引类似书的目录，用空间换时间，避免全表扫描。InnoDB 用 **B+ 树**：

- **矮胖**：多路平衡，千万级数据通常 3~4 层，查一行只要 3~4 次 IO。
- **数据只在叶子**：非叶子只存键，叶子存数据，且叶子之间用**双向链表**连接——天然支持范围查询和排序。

| 索引 | 叶子存什么 | 说明 |
|---|---|---|
| 聚簇索引 | 完整行数据 | 即主键，一张表一个 |
| 二级索引 | 主键值 | 取非索引列需**回表**（再查一次聚簇索引） |
| 覆盖索引 | — | 查询列都在索引里，免回表（Extra: Using index） |

**联合索引最左前缀**：`(a,b,c)` 可用于 a、a+b、a+b+c 的查询，范围查询右侧的列失效。理解这点，就知道为什么联合索引要把等值/高频列放前面。索引失效的常见情形（列上用函数/隐式类型转换、`LIKE '%xx'` 前导通配、不满足最左前缀）在 [03 · EXPLAIN](./03-功能) 结合执行计划讲。
