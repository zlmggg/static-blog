## 场景一 · 缓存穿透：查不存在的数据

**成因**：查询一个**数据库里也不存在**的数据（如恶意刷不存在的 ID），缓存里没有、DB 里也没有，于是每次请求都穿过缓存打到 DB。恶意攻击可以用大量不存在 ID 把 DB 打垮。

**解法**：
- **缓存空值**：DB 查不到也往缓存写个空值（短 TTL），下次同样的请求就被缓存挡住。
- **布隆过滤器**：在缓存前加一层，先判断 ID"是否可能存在"，不存在的直接拒绝，连缓存都不查。
- **参数校验**：明显非法的 ID（负数、超长）入口就拦掉。

## 场景二 · 缓存击穿：热点 key 过期瞬间

**成因**：某个**热点 key 过期**的那一瞬间，大量并发同时发现缓存没了，一起涌向 DB 重建缓存——DB 瞬间被压垮。和穿透的区别：击穿是"数据存在、只是缓存刚好过期"。

**解法**：
- **互斥锁**：缓存 miss 时只放一个线程去查库重建，其他线程等待重建结果，避免一窝蜂打 DB。
- **热点 key 逻辑过期/不过期**：热点数据不设物理 TTL，用逻辑过期字段 + 异步更新，避免"过期瞬间"。

## 场景三 · 缓存雪崩：大量 key 同时失效

**成因**：**大量 key 同时过期**，或 **Redis 整体宕机**，请求全压到 DB。和击穿的区别：雪崩是"大面积"，击穿是"单个热点"。

**解法**：
- 过期时间**加随机值**错开，避免同一时刻集体失效。
- Redis **集群高可用**（哨兵/Cluster，见 [02](./02-部署)），避免整体宕机。
- **多级缓存**（本地缓存 + Redis）、**限流降级**兜底，DB 前最后一道闸。

::: tip 三者一句话区分
穿透=查不存在的数据；击穿=单个热点 key 过期；雪崩=大面积 key 同时过期或 Redis 挂了。成因不同，解法各异。
:::

## 场景四 · 缓存与数据库一致性

**问题**：数据改了，缓存和 DB 谁先谁后？不一致怎么办？

常用 **Cache Aside（旁路缓存）**：
- **读**：先查缓存，miss 则查 DB 回填缓存。
- **写**：**先更新数据库，再删除缓存**（而不是更新缓存）。

为什么是"删缓存"而不是"更新缓存"？因为更新缓存在并发下更容易写脏（两个写请求交错），而删除让下次读时重新从 DB 加载，更稳。极端并发下仍可能短暂不一致，可用**延迟双删**（更新 DB 后删一次、隔几百毫秒再删一次）或**订阅 binlog**（如 Canal）异步刷缓存来兜底。

## 场景五 · 分布式锁

**需求**：多个进程/节点抢同一个资源，要保证同一时刻只有一个拿到锁。

```text
# 加锁：NX（不存在才设）+ PX（过期防死锁）+ 唯一标识（防误删）
SET lock:order 客户端唯一ID NX PX 10000
```

三个要点缺一不可：
- **NX**：保证互斥，只有一个能设成功。
- **PX 过期**：持锁进程崩了锁也能自动释放，防死锁。
- **值唯一**：释放时先判断"是不是自己的锁"，避免误删别人的锁。

**释放必须用 Lua** 保证"判断 + 删除"原子：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

如果先 GET 再 DEL 分两步，中间锁可能过期被别人拿到，你的 DEL 就误删了别人的锁——Lua 把两步合成原子操作才安全。复杂场景（可重入、看门狗自动续期）直接用 **Redisson**，别自己造轮子。
