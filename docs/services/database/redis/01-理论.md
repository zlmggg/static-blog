> 本篇讲"Redis 为什么快、数据怎么不丢、高可用怎么实现"。把单线程模型、持久化、哈希槽想明白，后面的缓存三大问题和集群运维才有根。动手装库去 [02 部署](./02-部署)。

## 一、它是什么：内存型 key-value 数据库

Redis（Remote Dictionary Server）是高性能的**内存型 key-value 数据库**。和 MySQL 把数据放磁盘不同，Redis 把数据放**内存**，读写不碰磁盘，所以快。它不只是缓存——还支持持久化、丰富数据类型、主从/哨兵/集群，常用于缓存、计数器、排行榜、分布式锁、消息队列、限流。

### 为什么快：四个原因叠加

| 原因 | 说明 |
|---|---|
| **纯内存** | 数据在内存，读写没有磁盘 IO（这是最根本的） |
| **IO 多路复用** | epoll + 事件驱动，一个线程照看大量连接（和 Nginx 同理） |
| **命令单线程** | 无锁、无线程切换、无竞态 |
| **数据结构高效** | 针对场景专门优化（如 ZSet 用跳表） |

### 单线程模型：6.0 的多线程到底指什么

这是最容易被误解的点：

- **6.0 之前**：核心全程单线程。
- **6.0 及以后**：**网络 IO 读写**引入多线程（解析请求、回写响应这些耗时的网络操作并行做），但**命令执行仍由主线程串行完成**。
- 持久化、异步删除、集群同步等辅助操作，本来就由后台线程做。

**为什么命令执行坚持单线程？** 因为单线程天然**原子、无锁竞争**——每条命令执行时不会被打断，`INCR` 这类操作不用加锁就是线程安全的。Redis 的瓶颈通常在内存和网络，不在 CPU，多线程执行命令反而引入锁开销、得不偿失。所以"Redis 6.0 多线程了"这句话要分清：**IO 多线程，执行仍单线程**。

## 二、五大数据类型：各管一类场景

Redis 的 value 不是只有字符串，五种基本类型各有擅长的场景：

| 类型 | 特点 | 典型场景 |
|---|---|---|
| **String** | 最基础，可存字符串/数字/二进制 | 缓存、计数器、分布式锁、session |
| **Hash** | 字段-值映射，可单字段更新 | 存对象（用户/商品），比 String 省 |
| **List** | 有序可重复、双端操作 | 消息队列、最新列表/时间线 |
| **Set** | 无序、自动去重、交并差集 | 标签、共同好友、抽奖 |
| **ZSet** | 成员带 score 排序 | 排行榜、热搜、带权重队列 |

还有几个专用类型：**Bitmap**（签到/在线状态，极省内存）、**HyperLogLog**（海量 UV 去重计数，约 0.81% 误差）、**Stream**（5.0 的消息队列，支持消费组/ACK）、**Geo**（附近的人/门店）。具体命令见 [03 功能](./03-功能)。

理解类型的关键是"**按场景选结构**"：存对象用 Hash 而不是把整个 JSON 塞 String（这样能单字段改）；排行榜用 ZSet 而不是自己排序；去重用 Set。选对结构，性能和内存都更优。

## 三、持久化：内存数据怎么不丢

数据在内存，宕机就没了——持久化就是把内存数据落盘的机制。两种思路：

### 3.1 RDB 快照

某时刻把内存**整体快照**写入 `dump.rdb`。`SAVE` 阻塞主线程（生产不用），`BGSAVE` fork 子进程去做（主线程继续服务）。

- **优点**：文件紧凑、恢复快、适合备份。
- **缺点**：两次快照之间宕机会丢这段数据；fork 大内存进程有开销。

### 3.2 AOF 追加日志

记录**每条写命令**，重启时重放恢复。`appendfsync` 控制刷盘频率：`always` 最安全（每条都刷，慢）、`everysec` 默认（最多丢 1 秒）、`no` 交给系统。

- **优点**：数据更安全。
- **缺点**：文件大、恢复慢，需要**重写**（BGREWRITEAOF）压缩——把冗余命令合并（如对同一 key 的 100 次 INCR 合成一条 SET）。

### 3.3 混合持久化（推荐）

4.0+ 在 AOF 重写时，**前半部分用 RDB 快照、后半部分追加增量命令**（`aof-use-rdb-preamble yes`）。这样恢复时先快速加载 RDB 主体，再重放少量增量——兼顾 RDB 的恢复速度和 AOF 的数据安全。

| 场景 | 选择 |
|---|---|
| 纯缓存、可丢 | 关闭持久化 |
| 不能丢 | AOF everysec / 混合 |
| 备份 | RDB 定期 + 异地 |

## 四、过期与淘汰：内存满了怎么办

### 过期删除：惰性 + 定期

设了 TTL 的 key 不是到点就立刻删，而是两种策略结合：**惰性删除**（访问时才检查是否过期）+ **定期删除**（周期抽样检查一批）。这样避免"集中删除大量过期 key"卡顿，也避免"只靠惰性"导致过期 key 堆积占内存。

### 内存淘汰：maxmemory 满了

当内存达到 `maxmemory`，再写入就要按策略淘汰旧 key：

| 策略 | 说明 |
|---|---|
| noeviction | 不淘汰，写报错（默认） |
| **allkeys-lru** | 所有 key 淘汰最久未用（**缓存常用**） |
| volatile-lru | 只在设过期的 key 中 LRU |
| allkeys-lfu / volatile-lfu | 按访问频率淘汰最少用（4.0） |
| volatile-ttl | 淘汰最快过期的 |

**LRU vs LFU**：LRU 看"最近有没有用"，LFU 看"用的频率高不高"。偶发批量扫描会污染 LRU（把冷数据误判成热），LFU 更抗这种干扰。做缓存一般选 allkeys-lru 或 allkeys-lfu。

## 五、事务与 Lua：原子性怎么保证

- **事务（MULTI/EXEC）**：把一组命令入队再顺序执行，`WATCH` 提供乐观锁。但 **Redis 事务不支持回滚**——运行期某条命令出错（如对字符串 INCR），其他命令仍会执行，需自己保证正确。
- **Lua 脚本**：整个脚本**原子执行**，中途不被打断，适合"组合操作"（如限流、释放锁）。需要真正原子的多步操作，用 Lua 而不是事务。

## 六、高可用三级：主从 → 哨兵 → Cluster

这三者解决不同层次的问题，是递进关系：

| 方案 | 解决什么 | 容量 | 故障切换 |
|---|---|---|---|
| **主从** | 读扩展 + 数据冗余 | 单机 | 手动 |
| **哨兵** | 高可用（自动切换） | 单机 | 自动 |
| **Cluster** | 高可用 + 水平扩容 | 分片 | 自动 |

- **主从复制**：一主多从。首次连接**全量同步**（主库 BGSAVE 生成 RDB 发给从库 + 缓冲期间新命令），之后**增量同步**（通过复制积压缓冲区 repl backlog 用 PSYNC 补发）。主从切换要手动。
- **哨兵 Sentinel**：在主从之上加一组哨兵进程做监控和**自动故障转移**。流程：单哨兵发现主无响应→**主观下线**；达到 quorum 票数→**客观下线**；哨兵选 leader，按优先级/复制偏移/runid 选一个从**提升为新主**；其他从指向新主，客户端经哨兵拿新主地址。
- **Cluster 集群**：哨兵保证了高可用，但数据仍在单主、容量扩不了。Cluster 用**分片**把数据分散到多主：共 **16384 个哈希槽**，`CRC16(key) % 16384` 定位槽，槽分给各主，每主配从，节点间用 Gossip 通信。多 key 操作需同槽，用 **hash tag**（`{user}:1`、`{user}:2` 都按 `user` 算槽）强制落同槽。

::: tip 为什么是 16384 个槽
作者 antirez 的解释：心跳包要携带槽位图，16384 槽 = 2KB，65536 槽 = 8KB，心跳带宽差 4 倍；而集群节点数通常不超过 1000，16384 槽足够分。这是带宽与扩展性的权衡。
:::
