# Nginx 03 · 功能详解

> 四篇制：[01 理论](./01-理论) · [02 部署](./02-部署) · [03 功能](./03-功能) · [04 实战](./04-实战)
> 本篇讲日常使用与配置，但每条规则都配上"为什么"。原理铺垫见 [01 理论](./01-理论)，这里聚焦"怎么用、为什么这么用、哪里最容易错"。

## 一、日常命令（中文详解）

Nginx 的运维动作几乎都围绕"改配置 → 校验 → 生效"这条线。下面这些命令就是这条线上的工具：

| 命令 | 作用 | 什么时候用 |
|---|---|---|
| `nginx -t` | 检查配置语法 | 每次改配置后、reload 前，必做 |
| `nginx -s reload` | 热加载配置，不断连接 | 改完配置生效 |
| `nginx -s quit` | 优雅停止，处理完再退 | 下线维护 |
| `nginx -s stop` | 立即停止 | 紧急止损 |
| `nginx -T` | 输出完整生效配置 | 排查"配置为什么不生效" |
| `nginx -V` | 版本 + 编译参数 | 确认有没有某模块 |
| `nginx -c /path` | 指定配置文件 | 多实例 / 编译安装 |

两个最值得理解的：

- **`reload` 为什么不断连接？** master 收到 reload 信号后，会先用新配置 fork 一批**新 worker**，让新 worker 接新连接，同时通知**旧 worker** "把手头的请求处理完就退"。新旧交替期间服务不中断，这就是"热加载"。所以 reload 前一定先 `nginx -t`——配置有语法错时 reload 会失败、旧配置继续跑，但如果你直接 restart 就会把站点搞挂。
- **`nginx -T` 是排障神器**：它把当前**真正生效**的完整配置（含所有 include 展开）打印出来。"我明明改了怎么没生效"十有八九是改错了文件、或 include 没加载到，`-T` 一看便知。

## 二、location 匹配算法（最易错，逐步讲）

先给结论，优先级从高到低：

```text
= 精确匹配  >  ^~ 前缀匹配  >  ~ / ~* 正则匹配  >  最长普通前缀  >  / 兜底
```

但光背结论容易忘，理解它的**判定流程**才不会再错。Nginx 拿到一个 URI 后是这样走的：

1. 先找有没有 `=` 精确匹配。**命中就立刻用，后面全不看**。
2. 再找所有普通前缀匹配（含 `^~`），记住**最长的那一个**。如果这个最长前缀带 `^~`，**就用它，且不再去查正则**。
3. 否则，按**书写顺序**逐个试正则 `~`（区分大小写）/`~*`（不区分），**第一个命中的正则就用**。
4. 如果一个正则都没命中，才回退用第 2 步记住的那个最长普通前缀。

关键反直觉点：**正则优先于普通前缀**（除非普通前缀带 `^~`），而且**正则之间按书写顺序、先命中先用**，普通前缀之间却按"最长"而非顺序。

### 逐步推演一个例子

```nginx
location = /health        { return 200 'ok'; }          # A 精确
location ^~ /static/      { root /var/www; }            # B 前缀，阻断正则
location ~* \.php$        { proxy_pass http://php; }     # C 正则
location /api/            { proxy_pass http://backend; } # D 普通前缀
location /                { try_files $uri $uri/ =404; } # E 兜底
```

- 请求 `/health`：第 1 步 A 精确命中 → 用 A，返回 ok。
- 请求 `/static/logo.png`：第 2 步最长前缀是 B 且带 `^~` → 用 B，**不再查正则**（即使后面有能匹配的正则也不看）。
- 请求 `/api/index.php`：第 2 步最长普通前缀是 D（`/api/`），但它不带 `^~`，所以继续第 3 步查正则；C `\.php$` 命中 → **用 C 而不是 D**。这就是"为什么我配了 /api/ 反代，php 请求却被转去 php 后端"——正则抢先了。
- 请求 `/api/user`：最长前缀 D，无 `^~`，查正则无命中 → 回退用 D。
- 请求 `/about`：只有 E 匹配 → 用 E。

::: tip 想让某个前缀"说了算"
如果希望 `/api/` 下的所有请求（哪怕 .php 结尾）都走反代，给它加 `^~`：`location ^~ /api/`。这样命中后直接阻断正则，不会再被 C 抢走。
:::

## 三、proxy_pass 带不带 URI（高频坑，讲原理）

`proxy_pass` 后面**带不带 URI 部分**，决定了转发给后端的路径怎么拼。规则只有一句话：

> **proxy_pass 不带 URI → 把原始请求路径原样传过去；带 URI → 用这个 URI 替换掉 location 匹配的那段前缀。**

```nginx
# 不带 URI（http://backend 后面没有路径）：原样转发
location /api/ { proxy_pass http://backend; }
# 请求 /api/user → 后端收到 /api/user

# 带 URI（http://backend/ 后面有 "/"）：替换前缀
location /api/ { proxy_pass http://backend/; }
# 请求 /api/user → 后端收到 /user   （/api/ 被替换成 /）
```

为什么会这样？因为带 URI 时，Nginx 把 `proxy_pass` 里的 URI 当作"目标根路径"，用请求 URI 中**去掉 location 前缀后的剩余部分**接在它后面。`/api/user` 去掉 `/api/` 剩 `user`，接到 `http://backend/` 后就是 `/user`。而不带 URI 时没有"目标根"可替换，只能整条原样转发。

::: warning 易错
后端 404 一大半是这里拼错了路径。判断方法：改完用 `curl -v` 或后端 access_log 看它**实际收到的 URI** 是不是你以为的那个。想要"削掉 /api 前缀"就带斜杠，想"原样保留"就不带。
:::

## 四、upstream 与负载策略（讲行为与适用）

```nginx
upstream backend {
    server 10.0.0.130:8080 weight=3;
    server 10.0.0.131:8080;
    keepalive 32;
}
server {
    location /api/ {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

各策略不是"哪个更好"，而是"适配哪种后端"：

| 策略 | 行为 | 适用场景 |
|---|---|---|
| 默认轮询 / weight | 按权重轮流分，weight 大的多分 | 后端性能不均（好机器多扛） |
| ip_hash | 同一客户端 IP 固定到同一台 | 会话粘滞：session 存在单机内存、没做共享时 |
| least_conn | 分给当前活跃连接最少的 | 请求耗时差异大（避免慢请求堆在一台） |

- **ip_hash 的代价**：它把"同一 IP"绑死到一台，一旦那台挂了，这批用户会失败转移；而且前面如果还有一层代理，所有请求看起来都来自代理 IP，ip_hash 就退化成"全压一台"。所以**优先做共享 session（Redis），而不是依赖 ip_hash**。
- **被动健康检查**：开源版 Nginx 默认是"被动"的——某台后端在 `fail_timeout`（默认 10s）内失败了 `max_fails`（默认 1）次，就暂时把它摘掉，过段时间再放回来试探。它不会主动发探测包。要主动健康检查得用 Nginx Plus 或第三方模块。

### keepalive 为什么要配两行

`upstream` 里的 `keepalive 32` 只是"允许缓存 32 条到后端的空闲长连接"，但**默认 Nginx 用 HTTP/1.0 连后端、且发 `Connection: close`**，后端处理完就关连接，长连接根本复用不起来。所以必须配套：

```nginx
proxy_http_version 1.1;        # 升到 1.1，默认才支持长连接
proxy_set_header Connection ""; # 清掉 close，告诉后端"别关"
```

三件齐了，到后端的 TCP 连接才能复用，省掉反复握手——高 QPS 下这对后端连接数压力影响很大。

## 五、反代必带请求头（讲真实 IP 链路）

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

为什么必须带？因为请求经过 Nginx 转手后，**后端看到的源 IP 变成了 Nginx 的 IP**，真实客户端 IP 丢了。不带这些头，后端的日志审计、按 IP 限流、风控全都失真。

- `X-Real-IP`：直接放客户端 IP（`$remote_addr`）。
- `X-Forwarded-For`（XFF）：是一个**链路列表**，格式 `客户端, 代理1, 代理2`。`$proxy_add_x_forwarded_for` 的作用是"把已有的 XFF 接上当前这一跳的 IP"，这样多层代理也能还原完整路径。后端取真实 IP 时通常取 XFF 的**第一个**（最左边是原始客户端），但要注意：XFF 可被客户端伪造，**只信任来自可信代理的那一段**。
- `X-Forwarded-Proto`：告诉后端原始请求是 http 还是 https，后端生成跳转链接、判断安全上下文时要用。

## 六、超时与 body 限制（讲 502 与 504 的区别）

| 指令 | 默认 | 说明 |
|---|---|---|
| `proxy_connect_timeout` | 60s | 与后端**建立连接**的超时 |
| `proxy_read_timeout` | 60s | 等后端**响应**的超时（两次读之间的间隔） |
| `proxy_send_timeout` | 60s | 向后端**发送请求**的超时 |
| `client_max_body_size` | 1m | 客户端请求体上限，超了返回 413 |

把超时和状态码对应起来，排障就有方向：

- **502 Bad Gateway**：Nginx 连上了（或试图连）后端，但后端**给了无效响应或干脆没响应**——后端进程挂了、端口错、upstream 地址写错、后端崩溃。问题在"后端有没有正常应答"。
- **504 Gateway Timeout**：后端**活着但太慢**，在 `proxy_read_timeout` 内没把响应给完。问题在"后端算得慢"，调大 read_timeout 只是缓解，根因往往是后端慢查询/慢接口。
- **413**：请求体超过 `client_max_body_size`，上传大文件常见，调大这个值（注意它是"客户端→Nginx"这一段，和后端无关）。

::: tip 504 别只会调大超时
`proxy_read_timeout` 调大能让慢请求不报错，但用户还是要等那么久。正确做法是先用 [04 · 日志](./04-实战) 的 `rt=$request_time` 找出慢在哪个接口，去优化后端，超时值只是兜底。
:::

## 七、缓冲机制（proxy_buffering 在干嘛）

反代时两侧速度不一致：后端可能"唰"一下把响应全推过来，客户端却慢慢收。`proxy_buffering on`（默认）让 Nginx 先把后端响应**缓冲到内存（不够再落磁盘）**，然后尽快释放后端连接，再按客户端的速度慢慢发。好处是**后端连接不被慢客户端拖住**，能去服务更多请求。

代价是 Nginx 自己多占内存/磁盘，且首字节延迟略增。对**流式响应**（SSE、长轮询、实时日志）要关掉缓冲 `proxy_buffering off`，否则数据被攒在缓冲里、客户端半天收不到一帧。相关参数 `proxy_buffers`、`proxy_buffer_size`、`proxy_busy_buffers_size` 控制缓冲大小，按需调。

## 八、指令频率分级

按使用频率给指令分三级，新手先掌握"每天用"那一列即可：

| 每天用 | 偶尔用 | 很少用 |
|---|---|---|
| server / listen / server_name / location / proxy_pass / root / index / try_files | upstream / keepalive / gzip / limit_req / ssl_certificate / rewrite / return | stub_status / geo / map / mirror / auth_request |

## 九、日志（排障的眼睛）

```nginx
log_format main '$remote_addr - $remote_user [$time_local] '
                '"$request" $status $body_bytes_sent '
                '"$http_referer" "$http_user_agent" rt=$request_time';
access_log /var/log/nginx/access.log main;
error_log  /var/log/nginx/error.log warn;
```

`rt=$request_time` 强烈建议加上——它是 Nginx 从读到请求到发完响应的总耗时，**排查慢请求全靠它**（配合 `$upstream_response_time` 还能区分"慢在后端"还是"慢在客户端传输"）。access_log 记每个请求的结果，error_log 记 Nginx 自身的异常（连不上后端、配置告警等），两者配合看。日志切割见 [logrotate](/commands/storage/logrotate)。
