# Prometheus 03 · 功能详解

> 四篇制：[01 理论](./01-理论) · [02 部署](./02-部署) · [03 功能](./03-功能) · [04 实战](./04-实战)
> 本篇是 PromQL 查询与 Exporter 采集。指标类型/标签模型见 [01 理论](./01-理论)。

## 一、PromQL 基础

### 即时向量与范围向量

- **即时向量**：某时刻的一组序列值，如 `node_memory_MemAvailable_bytes`。
- **范围向量**：一段时间窗口内的样本，如 `node_cpu_seconds_total[5m]`，**不能直接画图，要套 rate 等函数**。

### 标签选择器

```promql
http_requests_total{job="api", method="POST"}      # 精确匹配
http_requests_total{method!="GET"}                 # 不等于
http_requests_total{endpoint=~"/api/.*"}           # 正则匹配
http_requests_total{endpoint!~"/health.*"}         # 正则不匹配
```

### rate / increase：Counter 的正确用法

Counter 只增不减，直接看累计值没意义，要求和增速：

```promql
rate(http_requests_total[5m])         # 过去5分钟每秒平均增速（QPS）
increase(http_requests_total[1h])     # 过去1小时增量
irate(http_requests_total[5m])        # 瞬时增速（取最近两个点，更灵敏）
```

**为什么用 rate 不用 irate 做告警**：rate 用窗口内全部点算平均，平滑抗抖；irate 只看最近两点，灵敏但易误报。告警用 rate，看实时曲线用 irate。

### 聚合运算

```promql
sum(rate(http_requests_total[5m])) by (job)        # 按 job 汇总 QPS
avg(node_cpu_usage) by (instance)                  # 按实例平均
topk(5, sum(rate(http_requests_total[5m])) by (endpoint))   # QPS 前5接口
histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))  # P99延迟
```

`by` 保留指定标签、聚合掉其余；`without` 相反。Histogram 求分位数用 `histogram_quantile`，必须 `by (le)` 保留分桶标签。

### 常用主机 PromQL

```promql
# CPU 使用率
100 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) by (instance) * 100
# 内存使用率
(1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100
# 磁盘使用率
(1 - node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes) * 100
```

## 二、Exporter：把第三方数据翻译过来

Exporter 部署在被监控端，把软件现成数据翻译成 Prometheus 格式暴露在 `/metrics`。

| Exporter | 端口 | 采集对象 | 关键指标 |
|---|---|---|---|
| Node Exporter | 9100 | 主机 CPU/内存/磁盘/网络 | node_cpu_seconds_total、node_memory_MemAvailable_bytes |
| MySQLd Exporter | 9104 | [MySQL](/services/database/mysql/03-功能) | mysql_global_status_threads_connected、mysql_slave_status_slave_io_running |
| Redis Exporter | 9121 | [Redis](/services/database/redis/03-功能) | redis_memory_used_bytes、redis_connected_clients |
| Nginx Exporter | 9113 | [Nginx](/services/web/nginx/01-理论) stub_status | nginx_connections_active、nginx_http_requests_total |
| cAdvisor | 8080 | [容器](/services/container/docker/03-功能) | container_memory_working_set_bytes、container_cpu_usage_seconds_total |
| Blackbox Exporter | 9115 | HTTP/TCP/ICMP 探活 | probe_success、probe_duration_seconds |

### cAdvisor 容器监控要点

cAdvisor 通过 cgroups 采集每个容器的资源，一个 cAdvisor 只监控一台主机（K8s 用 DaemonSet，现代 kubelet 已内置）。查询要加 `{image!=""}` 过滤掉宿主机聚合序列：

```promql
sum(rate(container_cpu_usage_seconds_total{image!=""}[1m])) by (name) * 100
container_memory_working_set_bytes{image!=""} / container_spec_memory_limit_bytes{image!=""} * 100
```

::: warning 容器没设内存限制
`container_spec_memory_limit_bytes` 为 0 时上面除法得无穷大。生产必须给容器设内存限制；`container_memory_working_set_bytes` 是判断 OOM 的主要依据。
:::

## 三、relabel 标签重写

relabel 在采集前后改写标签：`relabel_configs` 在抓取前（改目标地址、过滤目标），`metric_relabel_configs` 在抓取后（丢弃高基数指标、改标签）。典型用途：服务发现来的目标打上环境标签、丢弃不要的指标省存储。

## 四、服务发现

静态配置要手改 targets，机器多了烦。服务发现自动更新目标清单：

- **file_sd**：读 JSON/YAML 文件，改文件即生效（不用重启），最灵活。
- **consul_sd / kubernetes_sd**：对接 Consul/K8s，新实例自动纳入。

K8s 里 Prometheus 用 kubernetes_sd 自动发现 Pod/Service/Node，新 Pod 起来自动监控，不用改配置。

## 五、记录规则

把常用复杂查询预先算好存成新序列，画图告警直接用，省重复计算：

```yaml
groups:
  - name: node_rules
    interval: 30s
    rules:
      - record: instance:node_cpu_usage:avg_rate5m
        expr: 100 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) by (instance) * 100
```

记录规则产出的指标名含冒号（`instance:node_cpu_usage:avg_rate5m`），这是冒号留给记录规则的原因。联邦中心节点只拉记录规则的聚合结果，大幅减少序列量。
