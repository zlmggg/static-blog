## 场景一 · 配一条能用的告警

告警分两段：**Prometheus 产生告警**（告警规则），**Alertmanager 发送告警**（路由）。

### Prometheus 告警规则

```yaml
# rules/alerts.yml
groups:
  - name: host_alerts
    rules:
      - alert: HostDown
        expr: up == 0
        for: 1m                      # 持续1分钟才报，避免抖动误报
        labels: { severity: critical }
        annotations:
          summary: "实例 {{ $labels.instance }} 失联"
      - alert: HighCpuUsage
        expr: 100 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) by (instance) * 100 > 85
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: "{{ $labels.instance }} CPU 超 85%"
```

`for` 是关键：条件持续满足这么久才真正 firing，避免瞬时抖动误报。`{{ $labels.instance }}` 模板取标签值。

### Alertmanager 路由

Alertmanager 收到告警后做**分组**（同类合并成一条）、**去重**、**静默**（维护期屏蔽）、**抑制**（critical 触发时压住 warning），再按路由发到邮件/钉钉/企微。配置见 [Alertmanager](/services/observability/alertmanager)。

## 场景二 · 分层联邦扩展

单机 Prometheus 目标多了扛不住。**联邦**让中心节点从下层节点的 `/federate` 端点拉聚合数据：下层各采一片，中心只汇总。像公司层级汇报——组长统计本组，经理只汇总组长报表。

中心节点配置四要素：

```yaml
  - job_name: 'federate-01'
    metrics_path: '/federate'        # 必须改，默认 /metrics 拿到的是从节点自身指标
    honor_labels: true               # 关键：不覆盖源标签，否则 instance 全变从节点地址
    params:
      'match[]':                     # 不写 match[] 不采任何数据
        - '{job="node_exporter"}'
        - '{__name__=~"node.*"}'
    static_configs:
      - targets: ['10.0.0.15:9090']
```

::: warning 联邦不是高可用、不是全量存储
联邦中心挂了全局视图就没了；上层只存匹配到的聚合指标。它适合做全局视图/汇总。真正 HA + 全量长期存储用 [VictoriaMetrics](./02-部署)。生产中心只拉记录规则的聚合结果，别用 `{__name__=~".+"}` 把明细全拉上来撑爆中心。
:::

下层扩容（加新主机）中心无需改动——这是分层联邦的扩展性。

## 场景三 · 四大常见坑

### 坑 1 · 序列爆炸撑爆内存

**现象**：内存磁盘快速上涨，日志 `too many series` / `series limit exceeded`，查询变慢。
**根因**：把 user_id/request_id/时间戳这类每次都变的值放进标签，标签值一变就是新序列，高基数让序列无限膨胀。
**解法**：去掉高基数标签；启动参数 `--storage.tsdb.max-series` 做保护。标签只放可枚举维度。

### 坑 2 · 目标 DOWN（up=0）

**现象**：Targets 页 DOWN，`dial tcp ... connect: connection refused`。
**根因**：Pull 要求网络可达。服务没起、只监听 127.0.0.1、防火墙/安全组没放通、IP 端口错。
**解法**：目标机 `ss -lntp | grep 9100` 看监听 → 改 0.0.0.0 → 放通端口 → 监控机 curl 验证。别急着重装软件。

### 坑 3 · Pushgateway 误推主机指标

**现象**：主机关机后大屏仍显示正常，漏报宕机。
**根因**：Pushgateway 数据一直保留，不因目标消失删除。
**解法**：主机一律 Node Exporter（拉不到自动 up=0），Pushgateway 只接批处理。

### 坑 4 · 磁盘写满

**根因**：没设 retention 或保留过长；高基数序列爆炸。
**解法**：retention.time + size 都设；排查高基数标签。见 [02 · 保留策略](./02-部署)。

## 常见问题 FAQ

| 现象 | 原因 | 解法 |
|---|---|---|
| 内存暴涨 too many series | 高基数标签 | 去掉唯一值标签 |
| 目标 DOWN | 网络/监听/防火墙 | ss + curl 逐层查 |
| 宕机漏报 | Pushgateway 推主机指标 | 改用 Node Exporter |
| 磁盘写满 | 无 retention/序列爆炸 | 设保留 + 查标签 |
| 联邦 instance 全变从节点 | 没设 honor_labels | honor_labels: true |
| 告警抖动误报 | 没设 for | 加 for 持续时间 |

OS 层排查：[ss](/commands/network/ss) 看端口、[top](/commands/system/top) 看资源、[df](/commands/storage/df) 看磁盘。更多见 [排障训练场](/cases/)。
